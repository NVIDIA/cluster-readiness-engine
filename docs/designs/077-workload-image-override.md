# ADR-077: Certification Workload Image Override

> **Status:** Accepted

## Context

Every catalog entry hardcodes its workload images. The base NCCL entries put `nvcr.io/nvidia/pytorch:26.01-py3` on the trainer (`pkg/catalog/entries/communication/nccl-all-reduce.yaml:163`) and on the worker and launcher containers of the TrainingRuntime dependency (`:45`, `:77`); the training entries do the same with `nvcr.io/nvidia/pytorch:25.08-py3` (`pkg/catalog/entries/training/nemotron5-8b.yaml:25`, `:113`). Platform overrides then swap images per environment: the AWS EFA blocks replace the trainer image with `public.ecr.aws/hpc-cloud/nccl-tests:...` (`nccl-all-reduce.yaml:223`, `:383`, `:431`) and the worker container image through a dependency merge (`pkg/catalog/entries/_lib/deps/aws-efa-runtime-patch-comm.yaml:19`).

Operators need to substitute these images without a rebuild: air-gapped sites mirror them into a private registry, security teams run patched builds, and staged NGC releases need validation against the curated tests. Today Certification offers only `imagePullSecrets` (authentication, not the reference itself; `api/v1alpha1/certification_types.go:201-205`), so the workaround is dropping a tier to WorkloadRun or a hand-authored Workflow and losing the curated catalog entirely. WorkloadRun already solved this for its tier: `spec.image` is a required field (`api/v1alpha1/workloadrun_types.go:182-185`) stamped at runtime construction (`pkg/controller/workloadrun_controller.go:306-331`, `pkg/platform/runtime.go:144-147`, `:262-264`). Certification has no counterpart.

Two properties of the catalog make this non-trivial:

- The image lives in more than one place per category, and overrides rewrite it after templates render. Any per-template solution would have to be threaded through every entry and every image-setting override, and a missed site would silently keep the old image.
- The pods carry init containers of two kinds. Workload-derived inits are stamped with the workload's own image by the catalog and must keep matching it: the MPI launcher's `fix-ssh-permissions` init container (`nccl-all-reduce.yaml:89-105`; the GB200 EFA patch pins it to the same nccl-tests image as the workers, `aws-gb200-efa-runtime-patch-comm.yaml:28-30`) and the training entries' `megatron-clone` init container (`nemotron5-8b.yaml:97-107`). Infrastructure inits must never change: GCP H100's `tcpxo-daemon` init container, whose image is Google's RxDM daemon, not a workload image at all (`pkg/catalog/entries/_lib/deps/gcp-h100-tcpxo-runtime-patch.yaml:42-43`).

There is an existing precedent for exactly this kind of post-resolve rewrite: `ApplyGangSchedulerToDependencies` runs after catalog and platform overrides resolve and rewrites the resolved TrainingRuntime dependencies in place, by explicit contract ("Callers must invoke this after overrides are resolved", `pkg/platform/gang_scheduler.go:47-50`). Its three call sites are the seam this ADR reuses: the Certification controller after `ApplyOverridesWithTracking` (`pkg/controller/certification_controller.go:506-511`) and both `nvcrectl certification render` paths after `render.ResolveWorkflow` (`pkg/certification/certification.go:208-211` for `--dry-run`, `:273-276` for offline).

## Decision

1. **Add an optional `image` field to `CategoryOptions`.** Settable at the Certification spec level (the options embed inline at `certification_types.go:362-363`) with the per-category value winning, exactly like every other option (`categories[].options`, `:332-335`). Empty means today's behavior: catalog and override images apply unchanged. Validation is deliberately light and consistent with `WorkloadRunSpec.Image`, which ships with `MinLength=1` and no pattern (`workloadrun_types.go:182-185`): the value lands in container image fields, never a shell, and a malformed reference is rejected visibly at pod creation or pull. No image-reference regex is attempted (the distribution reference grammar is long, drifts, and WorkloadRun has never needed it).

2. **Apply it post-resolve via a parallel function beside the gang scheduler.** A new `ApplyImageToDependencies` in `pkg/platform`, following the exact pattern of `ApplyGangSchedulerToDependencies` (`gang_scheduler.go:51-97`), plus a small `ApplyImageToJobTemplate` sibling for the trainer field, called at the same three post-resolve call sites listed in Context. No transform abstraction is introduced: two similar functions do not earn one (rule of three). If a third intent of this kind lands (open issue #212, labels on the TrainJob, is the candidate), that is the moment to refactor all of them into a named transform stage. Gang-scheduler code and goldens are untouched by this ADR.

3. **Pinned replacement semantics.** When the resolved image is non-empty, it replaces:
   - the trainer image, `jobTemplate.spec.workload.trainJob.trainer.image` (`nccl-all-reduce.yaml:150-163`; the field is Kubeflow's `Trainer.Image`, a `*string`, cf. `workloadrun_controller.go:464-465`),
   - the image of each replicated job's **primary workload container**, defined as the first entry of `template.spec.template.spec.containers`, in every resolved TrainingRuntime dependency, and
   - the image of each init container in that pod whose image **exactly equals** the primary's pre-override image (string equality on the full reference; a tag-only difference does not match).

   The equality rule is what separates workload-derived inits from infrastructure inits without coupling to any container name. The catalog derives `fix-ssh-permissions` and `megatron-clone` from the workload ref, so after overrides resolve they carry the exact image the primary carries and follow the override by construction; they must, because a prebaked user image can carry what the init provisions (in-image source such as Megatron-LM), and an init left on the catalog image would provision against the wrong image. Infrastructure inits like `tcpxo-daemon` carry a distinct reference (Google's RxDM daemon) and stay pinned by construction. Non-primary entries of `containers` are never touched, even when their image equals the primary's: only inits participate in the rule. Every catalog pod today has exactly one entry in `containers` (worker `nccl-all-reduce.yaml:29-64`, launcher `:76-88`, training worker `nemotron5-8b.yaml:111-113`). Because the function runs after catalog and platform overrides, the user's image wins over the AWS nccl-tests swap, on the trainer, the dependency containers, and the workload-derived inits. Only images are replaced; command, args, and env are untouched, which is the source of the footgun called out loudly in Consequences.

## Implementation

- `api/v1alpha1/certification_types.go`: `Image string` with `json:"image,omitempty"` on `CategoryOptions`, placed beside `imagePullSecrets` (`:201-205`), markers `+optional`, `+kubebuilder:validation:MinLength=1`, and a modest `+kubebuilder:validation:MaxLength=512`. Run `make manifests generate`.
- `pkg/controller/certification_controller.go`: `ResolveOptions` (`:603`) gains the non-empty-string branch `if override.Image != "" { resolved.Image = override.Image }`, following `StorageSize` (`:650-652`). The value is **not** added to `catalog.BuildConfig` (`pkg/catalog/catalog.go:27-133`) or `TemplateData` (`pkg/catalog/loader.go:73-208`): no template participates, by design.
- `pkg/platform/image.go` (new, beside `gang_scheduler.go`):
  - `ApplyImageToDependencies(deps []nvcrev1alpha1.DependencySpec, image string) error`. No-op when `image == ""`. Mirrors the gang scheduler skeleton: skip empty `Raw` (`gang_scheduler.go:58-60`), unmarshal errors are returned (`:62-64`), non-TrainingRuntime kinds are skipped byte-identically (`:66-68`), replicated jobs are walked via the shared `nestedSlice` (`:70-73`, `:102-120`). For each replicated job it walks to `template.spec.template.spec.containers` and, only when a non-empty containers list exists, sets `image` on the first entry. Unlike the gang scheduler's `ensureMap` labels write (`:125-132`), it never creates structure: a job with no containers is left alone.
  - `ApplyImageToJobTemplate(jt *nvcrev1alpha1.JobTemplateSpec, image string)`. No-op on empty image or when `Workload.TrainJob` or `Trainer` is nil (`api/v1alpha1/job_types.go:129-133`); otherwise sets `Trainer.Image = &image`. Post-override jobTemplate mutation in code has precedent in `applyPreCommands` (`pkg/controller/workflow_detect.go:806-828`).
- Call sites, immediately after the existing gang scheduler application (the two touch disjoint fields; the order is pinned anyway):
  - `pkg/controller/certification_controller.go:506-511`: `opts` is already resolved in scope (`:433`); pass `opts.Image` to both helpers against `workflowSpec`.
  - `pkg/certification/certification.go:208-211` (`--dry-run`) and `:273-276` (offline `resolveWorkflowsOffline`): resolve the per-workflow image with the already-exported `controller.ResolveOptions(&cert.Spec.CategoryOptions, cert.Spec.Categories[i].Options)` (the CLI already calls it at `:328`); `renderCertification` appends exactly one Workflow per category in category order (`:322`, `:396-409`), so index alignment holds. Both render paths stay pure data: the helpers touch only the in-memory spec, so offline render and `--dry-run` both show the substituted image with no cluster dependency.
- WorkloadRun: **no change**. `spec.image` exists and applies at runtime construction (`runtime.go:102-103` and the three builders). Unifying that stamping into the same post-resolve seam is optional future work, out of scope here.
- Docs: `docs/api-reference/certification.md` gains the field with the AWS EFA warning, and the air-gap FAQ entry (`docs/operations/faq.md`) folds the WorkloadRun and Certification paths into one prebake-then-point answer.

### Testing plan

- **Gang-scheduler goldens are untouched.** This ADR adds code beside the gang scheduler; it does not refactor it, so nothing regenerates.
- **testutil unit cases** (per the `/cre-test` pattern; parser precedent `pkg/platform/gang_scheduler_test.go:55-60`): new cases under `pkg/platform/testdata/apply-image-deps/` covering: MPI runtime with launcher and worker, both primary containers replaced and the `fix-ssh-permissions` init following (it carries the primary's pre-override image); the training shape with `megatron-clone` following for the same reason; the GCP tcpxo shape with `tcpxo-daemon` untouched (distinct reference); a pod with two entries in `containers` proving the second stays pinned even when its image equals the primary's (the rule is inits-only); an init on the same repository at a different tag proving equality is exact-string (it stays pinned); a ConfigMap, a ComputeDomain, and a PVC dependency byte-identical (the `rawUnchanged` projection); empty image as a full no-op; a TrainingRuntime with no containers list left alone.
- **Precedence**: render goldens under `pkg/certification/testdata/certification-render-image/` with a spec-level image and one category overriding it, proving per-category beats spec-level through `ResolveOptions`.
- **Render verification** per CLAUDE.md's nvcrectl procedure: build `bin/nvcrectl`, render an AWS H100 and an AWS GB200 cert carrying `image:`; the user image must appear where `public.ecr.aws/hpc-cloud/nccl-tests` appeared on the trainer and the primary containers, while `vpc.amazonaws.com/efa` counts stay exactly as CLAUDE.md tabulates. A grep for the EFA nccl-tests image then returns nothing on either target: on GB200 the EFA patch pins the launcher's `fix-ssh-permissions` init to the same nccl-tests image as the workers (`aws-gb200-efa-runtime-patch-comm.yaml:28-30`), so the equality rule carries it to the user image along with everything else. A GCP H100 render must still show the `tcpxo-daemon` image unchanged.
- **Integration case** `certification-image-override-nccl` under `cmd/integration/testdata/reconcile/`. Golden files are generated only after field-by-field review and maintainer approval, per CLAUDE.md.

## Rationale

- **The post-resolve seam is the only single point after every image writer.** Base templates, override `jobTemplate` merges, and override dependency merges all write images; the gang scheduler already established the seam that runs after all of them, with the ordering contract spelled out in its doc comment (`gang_scheduler.go:47-50`) and at the controller call site ("applied last so it wins", `certification_controller.go:506-507`).
- **A parallel function, not an abstraction.** Two functions with the same shape are cheaper to read than one abstraction with two closures, and refactoring the gang scheduler would put its goldens in play for zero user-visible gain. The rule of three sets the refactor trigger: issue #212 (TrainJob labels) is the anticipated third post-resolve intent, and folding all three into a named transform stage then is the right time.
- **First position, not container name.** The workload container is the first and only entry of `containers` in every catalog pod and in every runtime `pkg/platform` builds (`runtime.go:180`, `:337`, `:369`); container names are catalog-internal (`node` today) and keying the API to them would freeze them. Position is the invariant the builders already maintain.
- **Options pattern.** Global default with per-category override is how every deployment-specific knob enters Certification (`ResolveOptions`, `certification_controller.go:603-687`); the field behaves like `storageSize` and the other plain strings.

## Consequences

- **CRD schema change** to Certification only (`make manifests generate` regenerates the CRD under `helm/cluster-readiness-engine/crds/`). The field is optional; unset means byte-identical rendering to today.
- **Immutability.** Both specs are wholly immutable after creation (`self == oldSelf`, `certification_types.go:403`, `workloadrun_types.go:359`), so the image is fixed at creation; validating a new image means a new Certification.
- **The AWS EFA footgun, loudly.** On AWS H100 and GB200 the catalog deliberately swaps to the EFA nccl-tests image because the resolved command and args exec `/opt/amazon/openmpi/bin/mpirun` (`nccl-all-reduce.yaml:222`, `:387`) and `/opt/nccl-tests/build/all_reduce_perf` (`:217`, `:391`), and EFA transport requires the aws-ofi-nccl plugin bundled in that image (`:367-370`). The override replaces the image but never the command or args, so on those targets the operator's image **must** carry the EFA OFI plugin, OpenMPI at `/opt/amazon/openmpi`, and the nccl-tests binaries at `/opt/nccl-tests/build`, or the jobs fail. The docs must say this next to the field, and recommend basing custom AWS images on the upstream nccl-tests image. The same principle generalizes: the image must provide whatever the resolved entry executes (`/usr/local/bin/*_perf_mpi` and `/usr/local/mpi/bin/mpirun` for the base NCCL entries, a PyTorch/Megatron-capable environment for training).
- **Mixed-image pods only where infrastructure requires them.** Workload-derived inits (`fix-ssh-permissions`, `megatron-clone`) follow the override, so on most targets an overridden pod runs a single user image end to end. Only infrastructure init images stay on their catalog references and must therefore still be pullable in an air-gapped cluster (mirrored under their original names or covered by a registry mirror): today that is `tcpxo-daemon` on GCP H100. `imagePullSecrets` already applies pod-wide.
- **One image per category.** The same reference lands on the trainer, the MPI launcher, and the workers. Per-role images are a WorkloadRun/Workflow-tier concern, not a `CategoryOptions` one.

## Alternatives Considered

- **A per-entry template variable (`{{ .Image }}` through `BuildConfig`/`TemplateData`).** Rejected: every entry and every image-setting override must participate. The AWS blocks hardcode their own images in the entry (`nccl-all-reduce.yaml:223`, `:383`, `:431`) and in a `_lib` dependency patch (`aws-efa-runtime-patch-comm.yaml:19`); each would need templating, every future entry would need to remember the variable, and a missed site fails silently by keeping the old image. The post-resolve rewrite covers all of them at one seam.
- **A generic `spec.overrides` on Certification as the only mechanism** (reusing `OverrideSpec` as WorkloadRun does, `workloadrun_types.go:275-278`). Rejected outright, and not only for this feature; see Notes for the settled position. On the mechanics: an image-only intent must address the catalog-internal TrainingRuntime name (`nccl-all-reduce-runtime`), its replicated job names, and its container names, once per category. The dependency merge does support surgical by-name container patches (named-array merge, `pkg/controller/workflow_detect.go:684-714`), but only when every internal name is exactly right, and a mismatched name never errors: `mergeOrAppendDependency` appends the override as a brand-new dependency (`:606-608`), so a typo ships a stray resource and leaves the image unchanged. On the jobTemplate side, strategic merges of untagged lists replace them wholesale (`:611-615`), the exact footgun CLAUDE.md documents for `trainer.env`. That is a per-user, per-category, silently-failing encoding of a one-string intent.
- **Replacing all container images, including init containers and sidecars.** Rejected: it breaks `tcpxo-daemon` on GCP H100 (`gcp-h100-tcpxo-runtime-patch.yaml:42-43`), whose image is GCP infrastructure, and it would swap sidecars no catalog entry has yet defined the semantics for. Decision 3's equality rule takes exactly the safe subset: inits the catalog derived from the workload ref follow, everything with a distinct reference stays pinned, and no container name enters the API.
- **By-container-name targeting** (an API field naming which container to replace). Rejected: it couples the public API to catalog-internal names (every primary container is named `node` today: `nccl-all-reduce.yaml:46`, `:78`; `nodeJobName`, `runtime.go:41`), which must stay free to change. First-position is the convention the builders enforce and the catalog follows.
- **A named transform stage now** (a `WorkloadTransform` func type, one `ApplyWorkloadTransforms` entry point, gang scheduler refactored into it). Deferred, not rejected: with two consumers the abstraction buys nothing and forces re-proving the gang scheduler's behavior across its goldens. When a third post-resolve consumer lands (issue #212 is the candidate), refactor all three into the stage; this ADR keeps that door open by making the image helper an exact structural sibling of the gang scheduler helper.

## Notes

- **On future extensibility (settled position).** The maintainer has rejected a generic overrides surface on Certification. A structural override converts catalog internals (runtime names, replicated job names, container ordering) into de facto API and freezes catalog evolution; it also breaks result comparability, because a structurally overridden certification is no longer the curated test its report claims to be. The escape valve already exists as a tier drop, per the catalog-bypass answer in `docs/operations/faq.md` ("Can I use my own training workloads instead of the catalog?"): WorkloadRun with its `spec.overrides`, or a hand-authored Workflow CR. The standing policy this ADR operates under: a new `CategoryOptions` field requires a recurring operator intent with a validation-and-footgun story NVCRE can own (this ADR's Consequences section is that story for `image`); anything else routes to the WorkloadRun/Workflow tier.
- The catalog's inline `runtimePatches` under `jobTemplate` (`nccl-all-reduce.yaml:126-148`, `nemotron5-8b.yaml:27-42`) carry no images today, so the helpers do not walk them. If a future entry ever sets an image there, `ApplyImageToJobTemplate` must learn to.
- WorkloadRun and Certification now agree on init images: `BuildMPIRuntime` stamps the user image onto its `fix-ssh-permissions` init container at construction (`runtime.go:302-305`), and Decision 3's equality rule carries the catalog's workload-derived inits to the user image at the post-resolve seam. The two tiers reach the same pod shape by different mechanisms; the optional future unification of WorkloadRun's image stamping into this seam remains open but no longer papers over a behavioral difference.
- The image helpers and the gang scheduler application are order-independent (disjoint fields: `schedulerName` and the queue label versus `image`), but the call sites pin image-after-gang-scheduler so the seam reads deterministically.
- Offline render behavior deliberately differs from ADR-075's NIC detection: there is nothing to detect here, so `nvcrectl certification render` without a cluster shows exactly what the controller will create.
