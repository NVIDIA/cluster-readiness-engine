# ADR-092: HGX B300 Architecture Defaults, an On-Prem x86 HGX NIC Override, and a Fallback Event for Unknown Architectures

> **Status:** Proposed

## Context

`gpu.ParseProduct` (`pkg/gpu/product.go:35`) resolves an HGX B300 node, whose GFD label is `NVIDIA-B300-SXM6-AC`, to the architecture string `b300`. Nothing downstream knows that string. `pkg/catalog/entries/_lib/gpu-defaults.yaml` lists `b200`, `gb200`, and `gb300` but no `b300`, so every consumer of `GPUDefaults()` (`pkg/catalog/gpu_defaults.go:76-80`) receives the Go-side fallback of four GPUs and zero NICs (`fallbackGpusPerNode`, `:29`).

The hardware is an 8-GPU HGX baseboard, marketed as HGX B300 NVL16 (sixteen Blackwell Ultra dies across eight packages; `nvidia-smi` and GFD present eight GPUs): x86 host, NVSwitch confined to the chassis, no NVLink across nodes, eight ConnectX-8 NICs in the reference design, in both air-cooled and liquid-cooled chassis. It is a different machine from GB300, the Grace-Blackwell NVL72 rack (arm64, four GPUs per tray, MNNVL across trays). The two share a name prefix and nothing else that matters here, so matching B300 against the `gb300` gates would be wrong. Grace trays label their GPUs `GB300`, so no `B300`-prefixed label describes NVL72 hardware.

A customer ran NVCRE on an OpenShift cluster of HGX B300 nodes and hit four consequences of the missing entry, none of them signalled:

1. **The GPU count is halved.** `-N 4` on the `mpirun` line and `numProcPerNode: 4` on the TrainingRuntime leave four GPUs idle, and every bandwidth figure is measured at the wrong rank count. The run reports results anyway.
2. **No override matches.** The five `communication/` entries and both `training/` entries carry override blocks gated on `gb200`, `gb300`, `b200` (Nscale only), `h100`, `a100`, `l40`, `l40s`, and `rtxpro6000`. B300 renders from the bare base spec.
3. **`nicResourceName` and `mlnxPerNode` are inert.** Their only on-prem consumers are the ADR-075 fragments, gated on `gpuArchitecture: in: [gb200, gb300]` (`pkg/platform/overrides/workloadrun.yaml:357-361`, `pkg/catalog/entries/communication/nccl-all-gather.yaml:490-494`), and NIC auto-detection is gated the same way (`pkg/controller/nic_detect.go:38-40`). The customer set both fields in a WorkloadRun, saw no effect, and worked around it with `spec.resources`, which a Certification cannot do.
4. **The `--gpu-arch` flag and every other path disagree.** `ParseGPUArchFlag` (`pkg/catalog/gpu_defaults.go:108`) rejects `--gpu-arch b300` with the valid list. Every other way an architecture enters the system accepts it and sizes on the fallback silently: the controllers from node labels, the offline render from the nodeSelector (`pkg/certification/certification.go:499-501`, `pkg/workloadrun/workloadrun.go:152-153`), the dry-run render from the discovered nodes (`certification.go:193-199`), and `nvcrectl cluster info` (`pkg/cluster/cluster.go:131`). The customer's first run was an offline render with a `NVIDIA-B300` nodeSelector and no flag; it rendered `numProcPerNode: 4` with no output. The asymmetry is general: any architecture absent from the table is a hard error on the flag and a silent fallback everywhere else.

The customer's WorkloadRun also records the facts this design needs about the cluster. Node allocatable advertises `rdma/rdma_shared_device_a: 1k`, the k8s-rdma-shared-dev-plugin shape where one pooled resource stands in for every NIC, so the correct per-container request is one, exactly the case ADR-075 called out for `mlnxPerNode`. The NCCL environment the customer carried (`UCX_NET_DEVICES=mlx5_0:1`, `NCCL_NVLS_ENABLE=0`, `NCCL_DMABUF_ENABLE=1`, plus two NCCL defaults restated) came from a `numNodes: 1` run, so no inter-node setting was exercised, and the HCA pin is a per-site fact. There is no multi-node NCCL log yet.

B200 is the closest sibling. It has the same defaults shape (`gpu-defaults.yaml:37-39`: eight GPUs, eight NICs) and no on-prem override block; its only overrides are the Nscale ones (`in: [b200, gb300]` and `equals: b200`, thirteen blocks across the entries and `workloadrun.yaml`). Whatever gap exists for on-prem B300 exists identically for on-prem B200.

## Decision

1. **Add `b300` to `gpu-defaults.yaml`**, mirroring `b200`: `gpusPerNode: 8`, `mlnxPerNode: 8`. No `platformOverrides` entry. This fixes the rank count and makes `--gpu-arch b300` valid. Add `b300` parallelism rows to `training/nemotron5-8b/meta.yaml` and `training/nemotron5-56b/meta.yaml`, identical to their `b200` rows. The rows are redundant with each entry's `default` row today, as the `b200` rows are; they exist so a future change to `default` cannot silently retune B300.

2. **Add an on-prem x86 HGX override gated on `platform: onprem` and `gpuArchitecture: in: [b200, b300]`** to the seven entries ADR-075 touched and to `pkg/platform/overrides/workloadrun.yaml`. It carries exactly two things:
   - the `nvidia.com/gpu=present:NoSchedule` toleration, and
   - the NIC resource request, injected only when `nicResourceName` is set or auto-detected, with the per-container count from `mlnxPerNode`, under the same `{{- if .NicResourceName }}` guard ADR-075 established.

   It sets **no NCCL environment**. The NVL72 vars in `_lib/nccl/onprem-ib-env.yaml` (`NCCL_NVLS_ENABLE`, `NCCL_CUMEM_ENABLE`, `NCCL_P2P_NET_CHUNKSIZE`, `NCCL_MNNVL_ENABLE`, `:13-20`) are tuning for a different chassis, and the only field evidence for B300 is a single-node run. Fabric tuning for HGX lands in a later change once a two-node `NCCL_DEBUG=INFO` log exists.

3. **Author the override as a separate pair of `_lib/` fragments**, `_lib/deps/onprem-hgx-runtime-patch-comm.yaml` and `_lib/deps/onprem-hgx-runtime-patch-training.yaml`, derived from the ADR-075 fragments with three removals:
   - the arm64 toleration (`onprem-gb200-gb300-runtime-patch-comm.yaml:40`, `-training.yaml:39`);
   - the env block (`-training.yaml:35`);
   - the `mlPolicy.mpi.numProcPerNode` line (`-comm.yaml:15-17`). On the five MPI entries it is redundant: their base runtimes already set it (`nccl-all-reduce.yaml:16`, `nccl-all-gather.yaml:16`, `nccl-alltoall.yaml:16`). On the two per-node loopback entries it is harmful: their base runtimes declare `mlPolicy.torch` (`nccl-loopback.yaml:12-15`, `nccl-loopback-nvswitch.yaml:12-15`), dependency merge is a recursive map merge (`pkg/controller/workflow_detect.go:580-606`), and the TrainingRuntime CRD rejects a merged policy with both keys (`hack/crds/trainer.kubeflow.org_trainingruntimes.yaml:617`, "Only one of the policy can be configured").

   The GPU limits inside the NIC block are kept as a copy of the NVL72 fragment; they merge to the value the base already sets and are not load-bearing.

   The same two defects exist today in the NVL72 comm fragment (`onprem-gb200-gb300-runtime-patch-comm.yaml:15-17`), the Mistral comm fragment (`mistral-gb300-ib-runtime-patch-comm.yaml:9`), and the GCP GB200 comm fragment (`gcp-gb200-roce-runtime-patch-comm.yaml:9`), all of which the two loopback entries apply. This ADR fixes them the same way: the `mlPolicy` block is removed from all three fragments (redundant on the MPI entries, harmful on the loopback ones), and both loopback entries append `tolerate-all-runtime-patch.yaml` after each of those fragments. The NVL72 training fragment and its env are untouched, so on-prem GB200/GB300 MPI and training renders do not change; the on-prem GB300 loopback render changes from a two-policy runtime with a narrowed toleration list to a single `torch` policy with `operator: Exists`, which is the state the base entry declares.

   Tolerations have no merge key, so a fragment's `tolerations:` list replaces the base list (`workflow_detect.go:667-685`). The five MPI and training entries have no base tolerations, so there the HGX toleration is additive. The two loopback entries carry a tolerate-everything toleration (`nccl-loopback.yaml:40-41`, `nccl-loopback-nvswitch.yaml:40-41`); their HGX blocks list `deps/tolerate-all-runtime-patch.yaml` after the HGX fragment, exactly as the `nccl-loopback` Nscale block does (`nccl-loopback.yaml:438-439`), so the per-node entries keep tolerating everything. The `nccl-loopback-nvswitch` Nscale block applies `nscale-gpu.yaml`, which sets no tolerations, so it needs no patch.

4. **Widen the NIC auto-detection gate** to the same four architectures. `isOnPremNVL72` (`pkg/controller/nic_detect.go:38`) becomes `isOnPremNICOverrideTarget` and matches `gb200`, `gb300`, `b200`, and `b300` on `onprem`. The candidate rules, the every-node-at-count qualification, and the `NICResourceDetection` event are unchanged.

5. **B300 stays out of every NVL72 gate, and that is what keeps NVL72 machinery off it.** The ComputeDomain and DRA blocks, the clique topology key, and `NCCL_MNNVL_ENABLE` are all gated on `gpuArchitecture: in: [gb200, gb300]` with no platform matcher (`training/nemotron5-8b.yaml:289-291`, `communication/nccl-all-gather.yaml:334-336`, `_lib/overrides/gb200-topology-key.yaml:4-6`, `workloadrun.yaml:9-11`). Because `b300` is absent from those lists, an HGX B300 render carries no ComputeDomain, no DRA channel claim, and no clique key, which is correct for a chassis with no multi-node NVLink. `DefaultEnableMNNVL` (`pkg/controller/helpers.go:243`) is left unchanged; it only feeds one env var and already returns false for `b300`. A test pins that value so it is intentional rather than incidental.

6. **Emit a Warning event when an architecture falls back to the Go-side default.** The emission sites are the calls that size a workflow on the detected architecture: `createWorkflowForCategory` (`certification_controller.go:513`) and `buildWorkflowSpec` (`workloadrun_controller.go:438`; the `("", "")` seed at `:427` is the deliberate no-node baseline and emits nothing). When the architecture is non-empty, is not the `unknown` sentinel (`workflow_detect.go:30`), and is not listed in `gpu-defaults.yaml`, emit `GPUArchitectureDefaults` on the owning Certification or WorkloadRun. The sentinel exclusion is reachable only in `buildWorkflowSpec`: `createWorkflowForCategory` replaces `unknown` with the nodeSelector-derived architecture or fails (`certification_controller.go:497-507`), and `GPUArchFromNodeSelector` never returns `unknown`. A WorkloadRun over nodes with neither a product label nor a ResourceSlice `productName` therefore still sizes to four GPUs silently; that is a missing-label problem outside this ADR and is left as is. The message names the architecture, the assumed `gpusPerNode` and `mlnxPerNode`, and the fields that override them (`spec.gpusPerNode` and `spec.mlnxPerNode`, plus `categories[].options` on a Certification), and asks for an issue so the architecture can be added; it does not tell users to edit `gpu-defaults.yaml`, which is embedded in the binary.

   The message is computed where the counts are resolved but emitted only by the reconcile whose Workflow `Create` succeeds, next to `warnGCPH100DetectionFallbacks` (`certification_controller.go:724-726`) and in the matching branch of the WorkloadRun reconcile; a retry that finds the Workflow already there (cache lag, a failed status write) does not repeat it, so the event count is one. `buildWorkflowSpec` keeps its signature for its tests and wraps `buildWorkflowSpecWithWarning`, which returns the message alongside the spec. The result is one event per WorkloadRun and one per Certification category, as separate events, since the Certification's resourceVersion advances between categories and the recorder does not fold them (the same behavior `warnGCPH100DetectionFallbacks` documents at `certification_controller.go:732-739`).

   Every CLI render path prints the same message to stderr once: `renderCertification` (`pkg/certification/certification.go`, immediately after `gpuArch` is resolved at `:499-507` and before the per-category loop; `runCertificationRender` calls it once at `:219`, so this covers both the offline render and `--dry-run`), the WorkloadRun offline render (`pkg/workloadrun/workloadrun.go:162`), the WorkloadRun dry-run render (`workloadrun.go:608`; the two WorkloadRun entry points do not call each other), and `nvcrectl cluster info` (`pkg/cluster/cluster.go:131`). `applyNICDetection` (`certification.go:385`) prints nothing; its `GPUDefaults` call only resolves `mlnxPerNode`. `--gpu-arch` keeps rejecting unlisted values; the message covers the paths the flag does not reach.

   A Warning rather than a Normal event because the result is a guess standing in for a fact, the same posture as `GKENetworkDetection` and `TCPXOPluginDetection`, both emitted through `warnf` (`certification_controller.go:742,745`); `NICResourceDetection` is Normal because its outcome is the documented field-unset behavior, not a wrong number.

## Rationale

- **B200 is the right template.** Both are 8-GPU x86 HGX baseboards with NVSwitch inside the chassis. Mirroring its defaults is the smallest change that makes the rank count right.
- **A separate `when` block, not a widened list.** The NVL72 fragments bundle the NIC block with an arm64 toleration and NVL72 NCCL tuning. Handing an x86 chassis the arm64 toleration is harmless but wrong; handing it `NCCL_MNNVL_ENABLE` and the NVL72 chunk size is tuning for hardware it does not have. Separate fragments keep each set of facts attached to the hardware it was written for, and leave every existing on-prem golden untouched.
- **No env is better than guessed env.** The one field artifact is a single-node run. Shipping its HCA pin would break every other site; shipping `NCCL_NVLS_ENABLE=0` would cost intra-node bandwidth on NVSwitch with no multi-node evidence that it helps. The override still fixes scheduling and RDMA access, which is where the customer is actually stuck.
- **B200 joins the gate** because the gap is identical and gating on `b300` alone would leave the next HGX user filing the same issue.
- **The event closes the general asymmetry, not just this instance.** The next architecture missing from the table gets a Warning on the resource the operator is already watching, and a line on stderr from every render path, instead of a silent 4-GPU run.

## Consequences

- **On-prem B200 renders change.** They gain the GPU taint toleration (additive on the MPI and training entries; preserved as tolerate-everything on the loopback entries), and a NIC request when `nicResourceName` is set or auto-detection finds exactly one qualifying candidate. No golden renders an on-prem B200 target today (the only B200 cases are the Nscale ones), so the B200 behavior change adds goldens; the existing goldens that move are the ones listed in the testing plan. A site that advertises a single `rdma/*` resource at the default count of eight on every node will start requesting it with no configuration; the `NICResourceDetection` event explains any refusal, as on GB200/GB300.
- **Shared-device pools need `mlnxPerNode: 1`.** B200 and B300 default to eight, which a pooled resource advertised as `1k` does satisfy, so detection will request eight quota units of the pool. The k8s-rdma-shared-dev-plugin treats the count as a quota and grants the same device set for eight as for one, so the run works but consumes quota needlessly; the docs tell shared-plugin sites to set the count to one, as they already do for GB200/GB300.
- **WorkloadRun goldens move.** Every rendered WorkloadRun embeds the full override list, so one more block means one more entry in each golden, regardless of whether the block matches. This is mechanical churn and is listed in the testing plan.
- **`validation-results.md` is not updated.** Nothing has been validated on B300 hardware. The row is added when a run exists.
- **Fabric tuning for HGX is deferred**, and the docs say so. The follow-up needs a two-node NCCL log and the node YAML from a real cluster.
- **Metal3-provisioned HGX sites match nothing.** `metal3://` providerIDs resolve to `mistral` (`workflow_detect.go:70-71`, the detection trap ADR-075 documents), and every Mistral block is gated on `gb300`, so an HGX B200/B300 site provisioned by Cluster API plus Metal3 gets neither the HGX block nor the Mistral one from the controller: no toleration and no NIC request, with `--platform onprem` available only to `render`. This differs from NVL72, where such a site at least receives the Mistral block. The platform docs' Metal3 note says so; detection is unchanged here.
- **Override ordering stays load-bearing.** The HGX block sits after the NVL72 block and before any later tail blocks; ADR-088's `hostpath-rdma` block, when it lands, remains last.

## Alternatives Considered

- **Widen `in: [gb200, gb300]` to include `b300`.** Rejected: arm64 toleration and NVL72 NCCL tuning on an x86 chassis, and the NVL72 fragments would grow architecture conditionals that every existing on-prem golden then re-renders through.
- **Carry the customer's NCCL environment.** Rejected: `UCX_NET_DEVICES=mlx5_0:1` is a per-site HCA pin, ADR-075 already decided against pinning; `NCCL_NVLS_ENABLE=0` and `NCCL_DMABUF_ENABLE=1` are unjustified by a `numNodes: 1` run.
- **Gate the override on `b300` only.** Rejected: B200 has the identical gap and the identical hardware shape.
- **Defaults entry only, no override.** Rejected: it fixes the rank count but leaves `nicResourceName` and `mlnxPerNode` documented fields that do nothing on the hardware the customer has, and leaves Certification with no way to request RDMA devices on B300.
- **Copy the NVL72 comm fragment's `mlPolicy` line.** Rejected: redundant on MPI entries, and it merges a second policy into the torch-based loopback runtimes, which the CRD rejects.
- **Leave the existing fragments' `mlPolicy` line for a separate fix.** Rejected: the defect makes every on-prem, Mistral, and GCP GB200/GB300 loopback Certification fail at dependency creation, the fix is the same three-line removal in each fragment, and the ADR-092 render projection would otherwise ship a golden that pins the broken merge.
- **Normal event for the fallback.** Rejected in favour of Warning: the assumed count is wrong on every architecture that has eight GPUs, which is every architecture in the table except GB200/GB300.
- **Event only, no CLI output.** Rejected: the customer's first run was an offline render, which has no event stream.

## Notes

- **Pre-existing defect, fixed here.** Before this change, on-prem GB200/GB300, Mistral GB300, and GCP GB200/GB300 Certifications that included `nccl-loopback` or `nccl-loopback-nvswitch` rendered a TrainingRuntime with both `torch` and `mpi` policies, which the API server rejects at dependency creation, and lost the entry's tolerate-everything toleration. No integration case rendered any of those fragments on a loopback entry, so CI never created the object. The three fragment edits and six `tolerate-all-runtime-patch.yaml` additions in Decision 3 close both, and the three loopback integration cases keep them closed. Other fragments that still carry `mlPolicy.mpi` (`aws-gb200-efa-runtime-patch-comm.yaml`, `aws-gb300-roce-runtime-patch-comm.yaml`, `forge-ib-comm.yaml`) are applied only to MPI entries, where the line is redundant but harmless, and are left alone. `gcp-h100-tcpxo-runtime-patch.yaml` replaces the loopback entries' toleration list with the GPU-taint toleration on GCP H100; that is a narrowing of the same kind, left for a separate decision since the GCP H100 override was validated as is.
- **OpenShift.** The customer's cluster is OpenShift. The GPU toleration is harmless where the taint is absent. The MPI launcher's `sshd` failure on OpenShift (`SYS_CHROOT`) is issue #461 and is not addressed here.
- **`spec.resources` on WorkloadRun remains a valid escape hatch** for any resource the catalog does not know how to request. The override makes the typed fields work; it does not remove the generic path.
- **Product label variants.** `ParseProduct` takes the first segment before any hyphen or space, so `NVIDIA-B300`, `NVIDIA-B300-SXM6-AC`, a liquid-cooled suffix, and the ResourceSlice form `NVIDIA B300` all resolve to `b300`. `ConfigArch` (`pkg/catalog/catalog.go:255-260`) leaves `b300` unmapped, which is correct: the training entries ship one `configs/train.sh` each, and the architecture only selects a parallelism row.
- **ADR number.** 090 and 091 are claimed by PR #453; 092 is the next free number.
