# ADR-078: Preserve Externally Managed JobSet Across setup init and reset

> **Status:** Proposed

## Context

`nvcrectl setup init` installs Kubeflow Trainer 2.2.1 as Helm release `kubeflow-trainer` in `kubeflow-system`. That chart vendors JobSet as a subchart (`jobset.install` defaults to `true`, `fullnameOverride: jobset`). The chart's own values file documents the constraint we violate:

```yaml
jobset:
  # -- Whether to install jobset as a dependency managed by trainer.
  # This must be set to `false` if jobset controller/webhook has already been installed into the cluster.
  install: true
  # -- String to fully override jobset release name.
  fullnameOverride: jobset
```

[`trainerHelmUpgradeArgs`](../../pkg/setup/helm.go) never sets `jobset.install`. There is no Trainer `--set` passthrough. On a cluster that already has JobSet as its own Helm release (the field case: release `jobset` in `jobset-system`), `helm upgrade --install` refuses to adopt the cluster-scoped objects. The following abbreviated, rewrapped excerpt shows only the ownership-validation clause; it omits the conflicting object's kind/name and Helm error framing:

```text
invalid ownership metadata; key "meta.helm.sh/release-name" must equal
"kubeflow-trainer": current value is "jobset"
```

[`classifyTrainerInstallFailure`](../../pkg/setup/helm.go) requires all four substrings in the captured output: `conflict` and `secret` (case-insensitive), `.data.`, and the namespace `kubeflow-system` (ADR-073 decision 2). The ownership transcript lacks `conflict` and `.data.`, so it classifies as `failureClassOther` and [`handleTrainerInstallFailure`](../../pkg/setup/setup.go) returns the raw Helm output. Nothing points the operator at `jobset.install=false` or `--skip-phases=deps`.

The damaging half is cleanup. [`uninstallDepsPhase`](../../pkg/setup/setup.go) and [`recoverTrainerRelease`](../../pkg/setup/setup.go) both call `deleteCRDsByGroup(..., jobset.x-k8s.io)` with no owner check. Deleting `jobsets.jobset.x-k8s.io` cascades every JobSet in the cluster, including workloads that have nothing to do with NVCRE. ADR-073 decision 5 also refuses automatic recovery if **any** JobSet instance exists, which would block Trainer recovery forever on a cluster that already runs JobSet for other tenants.

The workaround today is to install Trainer by hand with `--set jobset.install=false`, then `nvcrectl setup init --skip-phases=deps`, and to pass `--skip-phases=deps` on reset as well. Issue #335 is that `setup` must do this itself.

This record does not reopen ADR-073's SSA recovery for webhook Secret `.data` conflicts (issue #180). Skip-when-deployed (subject to decision 2's CRD existence check), attempt-then-classify for that class, no `--force`/`--take-ownership`, TrainJob / non-Helm TrainingRuntime gating, and the one-attempt recovery arm stay as written. This record proposes superseding ADR-073's JobSet CRD deletion and JobSet-instance recovery gating, and reversing its accepted policy of deleting unrelated resources in `kubeflow-system` during automatic recovery. ADR-073 explicitly accepts losing a user ConfigMap in that namespace; under decision 4 here, an observed resource of that kind instead blocks recovery, subject to the quiescence prerequisite and repeated checks below. These amendments take effect only after this proposal is accepted and implemented.

## Decision

1. **Separate controller ownership from CRD provenance.** The published Trainer 2.2.1 archive stores JobSet's CRD at `charts/jobset/crds/jobset.x-k8s.io_jobsets.yaml`. It has no Helm release ownership metadata, and Helm installs `crds/` resources without adding that metadata. An unlabeled CRD therefore does **not** distinguish an external install from an existing bundled install.

   Start the ownership probe with one `Get` for `jobsets.jobset.x-k8s.io`. A `NotFound` response selects `absent` immediately, without reading release manifests, controller resources, or JobSet instances for this probe. Any other read error selects `unknown`. When the CRD exists, resolve the JobSet controller mode from the exact Trainer release's stored manifest and live JobSet controller, RBAC, and webhook resources. Use the pinned subchart's resource identities and webhook service references; do not assume the external Helm release is named `jobset`. Read the release manifest before uninstalling it, including failed/partial release state. Values alone are insufficient: `jobset.install=true` does not prove that the release created a pre-existing CRD.

   A live resource belongs to the bundled release only when its `app.kubernetes.io/managed-by` **label** is `Helm` and its `meta.helm.sh/release-name` and `meta.helm.sh/release-namespace` **annotations** are `kubeflow-trainer` and `kubeflow-system`. A same-named release in another namespace is external. Missing CRD annotations never override positive bundled controller/release evidence.

   | State | Meaning |
   |---|---|
   | `absent` | The JobSet CRD `Get` returns `NotFound`; no further ownership probing is required |
   | `bundled` | The Trainer release manifest or its live JobSet resources identify the bundled controller, with no conflicting external ownership |
   | `external` | External controller ownership is established |
   | `crd-only` | The CRD exists, and successful inspection finds no JobSet controller or supporting resources, no bundled or conflicting release evidence, and no JobSet instances cluster-wide |
   | `unknown` | Required reads fail, release/live-resource evidence conflicts, or a CRD exists without an identifiable controller and the `crd-only` conditions are not satisfied |

   CRD existence alone never establishes an external controller. The `crd-only` state requires successful inspection of controller and supporting resources, including RBAC and webhooks, and a successful cluster-wide JobSet list returning no instances. Leftover supporting resources, conflicting release evidence, or JobSets without an identifiable controller require operator reconciliation. Failed reads are not equivalent to absent resources. The implementation must test the detector against the published chart's actual resource identities and an unlabeled CRD, not fixtures that invent CRD ownership labels.

2. **Choose the subchart value before mutating the Trainer release.** Before accepting `planTrainerPhase`'s pinned-version skip or proceeding with an install/upgrade, read `jobsets.jobset.x-k8s.io`. A required read failure stops the dependency phase with the lookup error, including on the skip path. A deployed release at the pinned version remains skipped when the CRD exists; that path needs no full ownership probe and does not certify controller health or schema compatibility. Resolve ownership under decision 1 for every install or upgrade that would actually run.

   **A missing CRD on an existing installation requires operator repair.** When Trainer is deployed at either the pinned version or another version and the JobSet CRD is absent, stop before skipping or running Helm. Apply the same refusal when the selected action would upgrade another existing release. `helm upgrade --install` does not install the chart's `crds/` directory on its upgrade path, and a skipped release cannot restore it. Report the missing CRD and require the operator to restore a compatible JobSet CRD using the intended JobSet installation's CRD procedure, wait for it to be established, then rerun `setup init`. Restoring the CRD does not restore instances lost when it was deleted. Do not automatically apply a schema, uninstall Trainer, or enter destructive recovery solely because this CRD is missing. Automatic shared-CRD reconciliation remains deferred under decision 3.

   | State | `jobset.install` |
   |---|---|
   | `absent`, `bundled`, or `crd-only` | Keep enabled; omit the override |
   | `external` | Pass `--set jobset.install=false` |
   | `unknown` | Stop before Helm mutation; print the blocking evidence and the manual Trainer installation plus `nvcrectl setup init --skip-phases=deps` path |

   For `unknown`, explain that the operator must resolve the reported ownership uncertainty, install Trainer manually with the appropriate `jobset.install` value, and then run `nvcrectl setup init --skip-phases=deps`. Print that command explicitly. Recommend `jobset.install=false` only after external ownership is confirmed; do not prescribe either value from ambiguous evidence. This manual fallback is the supported escape path; no `--jobset-mode` override is introduced.

   **The manual fallback still installs NVCRE.** Every printed `nvcrectl setup init --skip-phases=deps` fallback must state that it skips Trainer setup only. Use a released CLI whose matching NVCRE chart is available, or supply `--version <nvcre-chart-version>` explicitly (required when the CLI reports a dev version, including an untagged source build). The selected chart version must be reachable at the default chart location or at an optional `--chart-ref <nvcre-chart-reference>`, with any required registry access. `--chart-ref` alone does not satisfy a dev build's version requirement. For that build, print `nvcrectl setup init --skip-phases=deps --version <nvcre-chart-version>`, with the optional chart-reference override explained separately. These flags select the NVCRE chart, not the manually installed Trainer chart. Do not recommend `--skip-phases=deps,helm` as a current workaround: the existing CLI does not gate the Helm phase. The phase-gating implementation below is a prerequisite for the future dependency-only UAT commands.

   For `absent`, proceed with the normal bundled Helm install path only when the release-state decision actually selects a fresh installation; an existing release's upgrade path requires the repair above. The short circuit establishes CRD absence, not absence of every controller or supporting object. If leftover objects collide, Helm's ownership checks reject the install and decision 5 supplies targeted guidance; do not use `--take-ownership`. The short circuit only skips ownership probing for install selection. It does not bypass the existing release-state check or decision 4's safety checks before destructive recovery.

   Never disable a subchart already present in the Trainer release merely because its CRD lacks annotations: upgrading with `false` can remove the controller. Mixed bundled/external evidence requires operator reconciliation rather than guessing. `jobset.controller.tolerations[0].operator=Exists` may remain; it is unused with the subchart disabled.

   Capture the selected mode before recovery uninstalls the release and reuse it for reinstall. Revalidate conflicting live ownership before destructive operations; do not classify a retained bundled CRD as external solely because recovery has just removed its controller and release record.

   An independent init after a completed reset inspects the retained CRD and remaining resources again. When the `crd-only` conditions hold, install the bundled controller while retaining the existing CRD. Helm's `crds/` installation path skips the existing CRD; controller installation does not establish its creation provenance. Report that the bundled controller will be installed using the retained CRD. If JobSets remain without an identifiable controller, stop rather than start reconciling workloads whose intended management is unknown. This restores the ordinary bundled reset/init cycle when no JobSets or conflicting resources remain.

   This pre-probe concerns observable installation ownership, not prediction of ADR-073's SSA Secret conflicts.

3. **Retain JobSet CRDs in reset and recovery.** Neither a bundled controller nor a release manifest proves that NVCRE originally created the shared CRD: Helm can reuse an existing CRD. Existing releases have no trustworthy creation record. Remove the unconditional JobSet `deleteCRDsByGroup` calls and preserve the CRD in every ownership state, including bundled installs. Do not retrofit ownership metadata onto existing CRDs or infer deletion permission from controller ownership.

   This deliberately changes the original proposal's bundled-cleanup behavior: positive creation provenance is unavailable, so automatic CRD deletion is deferred. A future design could record creation provenance, but that is not part of this fix. Trainer CRDs remain cleanup targets, subject to decision 4's repeated checks during recovery.

   **Schema refresh is operator-managed.** Helm does not update JobSet's `crds/` schema during an upgrade, and a fresh install skips an existing CRD. Consequently, this design leaves an existing JobSet CRD schema unchanged through Trainer upgrades, recovery, and reset/init, for both bundled and external installations. The NVCRE chart's `applyChartCRDs` path (issue #145) is not extended to Trainer/JobSet in this change. Automatic reconciliation of the shared JobSet CRD is deferred to a separate design covering schema compatibility, stored-version migration, and coordination with external controllers and workloads. Until then, operators must assess cluster-wide consumers and follow the JobSet release's CRD upgrade and migration procedure before using features that require a newer schema. Reset/init is not a schema-upgrade procedure, and deleting the CRD is not the default upgrade guidance.

   `printRetainedResources` reports the retained JobSet CRD and explains that deleting it destroys JobSets across all namespaces. Recovery plans and manual recovery instructions always omit JobSet CRD deletion. A standalone manual cleanup command must be described as an operator decision after inspecting cluster-wide use, not as a required recovery step. Helm uninstall still removes bundled controller resources; preservation of the CRD does not promise preservation of a bundled controller.

   **Retained-output contract:** when the dependency reset phase ran, a present JobSet CRD gets a warning-only retained-resource entry explaining the cluster-wide cascade risk. Do not print a `kubectl delete crd` command for this entry or reuse the existing namespace/Secret cleanup-command shape. A failed lookup uses the same warning-only entry with “may remain” and the lookup error; a confirmed absent CRD is omitted. With `--skip-phases=deps`, omit the JobSet CRD entry and its lookup, just as the Trainer namespace entry is omitted: the dependency phase made no retention decision. The implementation must support explanatory retained-resource text without a deletion command.

   **Reset inspection contract:** reset does not need the JobSet ownership detector or the recovery namespace inventory to authorize its existing Trainer release uninstall. It uninstalls only the configured `kubeflow-trainer` release in `kubeflow-system`, leaves that namespace intact, and never deletes JobSet CRDs. Ownership-inspection failures therefore do not block reset or trigger fallback cleanup. The retained-resource lookup is best effort: a failed lookup prints that the JobSet CRD *may remain*, with the lookup error, rather than claiming it is absent. Helm uninstall and Trainer CRD cleanup failures still propagate normally. `--skip-phases=deps` continues to bypass dependency removal. This is an explicit reset operation, not automatic recovery; the recovery safety gate does not apply to it.

4. **Gate recovery on resources representing user workloads, configuration, or storage, as well as JobSet controller disruption.** Retaining the CRD alone does not make release uninstall or namespace deletion safe. Derived objects that no controller owns and that Kubernetes rebuilds from primary resources are excluded from the recovery inventory: Events (core and `events.k8s.io`), core `Endpoints`, and EndpointSlices (`discovery.k8s.io`). Their deletion is an accepted consequence. Before uninstalling Trainer or deleting `kubeflow-system`:

   - Continue to block on TrainJobs and non-Helm TrainingRuntime/ClusterTrainingRuntime instances as ADR-073 requires.
   - When the bundled JobSet controller would be uninstalled, any JobSet instance blocks automatic recovery, even though its CRD is retained.
   - When JobSet is external, instances outside `kubeflow-system` do not alone block recovery. Any JobSet instance inside `kubeflow-system` does block it because namespace deletion destroys that instance.
   - Verify that no external JobSet controller or supporting resource within the protected inventory resides in `kubeflow-system`. Inspect namespaced resources and their ownership, including webhook service targets. Inventory namespaced resource types representing workloads, configuration, or storage, including Pods, Services, Secrets, ConfigMaps, PVCs, and custom resources. Exclude Events (both core and `events.k8s.io`), core `Endpoints`, and EndpointSlices (`discovery.k8s.io`) entirely: do not list them for this gate or prove their lineage. These share one shape: the endpoints controller and the event machinery create them from a primary resource, they carry no owner references (core `Endpoints` copies the Service's labels, including `app.kubernetes.io/managed-by: Helm`, but not its annotations), and they are rebuilt automatically when the primary resource returns. The Trainer chart renders the `kubeflow-trainer-controller-manager` Service unconditionally, even with `jobset.install=false`, so a core `Endpoints` object is present in `kubeflow-system` on every cluster; inventorying it would block recovery everywhere. The same evidentiary rule governs any future exclusion, but an unknown kind remains protected until a concrete fixture and rationale establish that it is ownerless, derived from a protected primary resource, and automatically rebuilt. Other discoverable namespaced resource types remain protected by default. Refuse namespace deletion when foreign or unclassified protected resources could be removed; do not rely only on default controller names or labels. Unrelated foreign objects such as a user ConfigMap also block recovery.
   - Classify namespace inventory against the exact Trainer release manifest and live ownership. Permit a release resource only when its identity and complete Helm ownership agree. For controller-created objects such as ReplicaSets and Pods, follow owner references by UID to a verified release resource; a copied label or a dangling, cyclic, or mismatched owner reference is not sufficient. Unknown descendants block recovery. This inventory permission never overrides the TrainJob, runtime, or JobSet blockers above.
   - Use a small, explicit allowlist for protected resources that are expected outside the rendered manifest: the namespace's default ServiceAccount and `kube-root-ca.crt` ConfigMap, the exact Trainer release's Helm storage records, and leader-election Leases whose relationship to verified release resources is established. Define a predicate per kind using its expected identity, content, and ownership/controller evidence; a name or namespace alone is not permission. Unexpected custom fields or references, unrelated release records, and anything outside these predicates block recovery. Add further exceptions only with a concrete fixture and rationale; do not blanket-allow Secrets, ConfigMaps, or Leases. Events, core `Endpoints`, and EndpointSlices are exclusions from the inventory, not conditional allowlist entries.
   - Failed discovery needed to enumerate protected resource types, an incomplete protected inventory, or unresolved ownership within that inventory blocks automatic recovery. A restricted kubeconfig must permit the required discovery and listing of protected resources in `kubeflow-system`, plus the cluster-wide workload checks above. On permission failure, report the affected API resource, namespace or cluster scope, and required operation so the operator can obtain access and retry. Missing list permissions for excluded Events, core `Endpoints`, or EndpointSlices do not block this gate. `--auto-approve` bypasses the prompt, not these checks.

   **Quiescence is an operator prerequisite.** Before recovery and until it completes or stops, the operator must prevent concurrent protected-resource writes into `kubeflow-system`, Trainer custom-resource writes cluster-wide, and JobSet creation cluster-wide when recovery removes the bundled controller. Recovery's own cleanup and reinstall are expected changes. External JobSets elsewhere may continue under an external controller only while these boundaries hold. Print this prerequisite in the recovery plan, including with `--auto-approve`; that flag neither establishes quiescence nor bypasses inspection. If the operator cannot maintain these conditions, use operator-managed recovery. NVCRE does not stop externally owned controllers or install a write barrier in this change.

   **Recheck at destructive boundaries.** Run the initial gate before presenting the recovery plan, then repeat the complete gate after confirmation immediately before Helm uninstall. Recheck the cluster-wide Trainer workload blockers immediately before each Trainer CRD deletion, and the applicable JobSet blockers before proceeding with further cleanup. Immediately before namespace deletion, perform fresh discovery and a final protected namespace inventory with the same exclusions and classification rules. Any blocker or required inspection failure stops further recovery; the initial gate never authorizes skipping a later check.

   **Compare against expected cleanup, not an identical inventory.** Preserve the exact release manifest, namespace UID, and verified object identities, UIDs, ownership chains, and classification evidence before uninstall removes release records and owners. Revalidate remaining objects against that evidence and the per-kind predicates. Expected removals and cleanup-related metadata changes do not alone block recovery. New protected objects, replacement UIDs, changed ownership, or changes that invalidate classification do block it. A previously verified descendant may retain its classification after recovery removes its owner only when its UID and ownership evidence still match; a new dangling reference is not sufficient. Account for Trainer CRDs intentionally removed by this recovery when refreshing discovery; unexplained API disappearance, failed discovery, or an incomplete list is not an empty inventory. Delete only the inspected namespace using its UID as a delete precondition; this prevents deletion of a replacement namespace, but does not protect against new objects within the same namespace.

   **These checks do not prove the absence of concurrent writers.** Inventory is observational and is not atomic with Helm uninstall, CRD deletion, or namespace deletion. A write can still occur between a successful check and its destructive operation. Kubernetes `NamespaceLifecycle` rejects new creates in a terminating namespace; starting termination is already destructive and cannot serve as a reversible inventory barrier. The protection contract therefore depends on operator-maintained quiescence, with repeated checks reducing exposure and detecting observed violations. It does not guarantee preservation under concurrent writes.

   On refusal, report the blocking resources or failed inspection and do not print an unconditional namespace-delete command as a safe workaround. A refusal before uninstall leaves recovery cleanup unstarted. A later refusal reports recovery as partially completed, identifies completed actions and any uncertain outcomes, and stops without further deletion or automatic reinstall. Trainer may already be uninstalled and its CRDs removed; do not claim rollback or that nothing was changed. Manual guidance must preserve the same boundaries and explain the remaining operator recovery work. Reset does not delete `kubeflow-system` today; this change must not add namespace deletion to reset.

5. **Provide narrowly matched ownership guidance on every install failure path.** Add `failureClassJobSetOwnership` only when the same Helm error identifies `invalid ownership metadata` and a concrete JobSet resource kind/name from the subchart or independently observed JobSet resources. A bare ownership phrase, unrelated Trainer resource, or incidental occurrence of the word JobSet is insufficient. Keep unmatched ownership errors generic and retain the original transcript.

   Pin the classifier with a diagnostics golden fixture captured from a real Helm collision between standalone JobSet and the published Trainer 2.2.1 chart. Preserve the complete error framing, conflicting cluster-scoped resource kind/name generated with `fullnameOverride: jobset`, annotation-validation details, and original line breaks. Record the Helm/chart versions and reproduction commands alongside the fixture. The abbreviated Context excerpt is not sufficient classifier input. Assert both the classification and emitted guidance using the existing `testutil.TestCaseParser` pattern; include negative cases with unrelated ownership errors and incidental JobSet mentions so matching cannot degrade into bare word checks. This fixture is required in the implementation PR.

   Route captured failures from both `trainerActionInstall` (including fresh and unknown-release states) and `trainerActionAttemptRecover` through a common diagnostic step. Do not accidentally enable SSA recovery for fresh installs: ownership diagnostics are shared, while the existing ADR-073 recovery eligibility remains unchanged. Recovery reinstall failures also receive these diagnostics without starting another recovery attempt.

   For the JobSet ownership class, report the conflicting object and explain the external-JobSet path: install Trainer with `jobset.install=false`, then `setup init --skip-phases=deps`. Also document `setup reset --skip-phases=deps` for affected older CLI versions. If evidence is ambiguous, describe the workaround as conditional on confirming external ownership; do not assert that the conflicting object necessarily belongs to another release. Never uninstall Trainer, delete CRDs, or delete the namespace in response to this error class. Match this class before considering SSA recovery.

6. **Choose automatic detection; leave generic Trainer values passthrough outside this change.** Issue #335 requests automatic detection or, at minimum, Trainer chart values passthrough. This design chooses automatic detection and the targeted `jobset.install` override. Generic `--set` / `--values` passthrough is outside this change; this does not rule out a separate future proposal. Operators needing custom values can install Trainer manually and run `nvcrectl setup init --skip-phases=deps`.

   No JobSet version gate is introduced. External controller compatibility remains the operator's responsibility; document that the controller must support the JobSet API and features required by Trainer 2.2.1. A present CRD alone does not prove controller health or compatibility.

## Implementation

- **Ownership observation:** add a shared observation structure containing controller mode, evidence, and inspection errors. Perform the JobSet CRD `Get` before accepting a pinned-version skip or proceeding with install/upgrade. Apply decision 2's missing-CRD repair refusal for existing installations; a present CRD permits the pinned-version skip without full ownership inspection. For the ownership probe: return `absent` immediately on `NotFound`, `unknown` on other errors, and inspect the exact Trainer release manifest and relevant live resources only when the CRD exists. Reset does not depend on this detector; its CRD-retention rule is unconditional. Keep CRD existence separate from controller ownership; require the full release-name/namespace identity for live bundled resources. Preserve the observation across recovery, with conflict checks and the required recovery inventory before destructive actions regardless of the install-selection short circuit.
- **Phase selection:** add a `helm` phase constant, gate the complete NVCRE Helm phase on it, and validate `--skip-phases` against the known phase names for both `init` and `reset`. On init, the gate includes controller pull-secret setup and the NVCRE Helm install. On reset, it includes the NVCRE Helm uninstall and NVCRE CRD cleanup. Required by the lifecycle UAT and correct on its own: today `--skip-phases=helm` is accepted and ignored.
- **Helm arguments and diagnostics:** extend `trainerHelmUpgradeArgs` and the injected `trainerHelm.install` operation to carry the selected mode. Print the manual Trainer installation and `nvcrectl setup init --skip-phases=deps` fallback whenever the selected mode is `unknown`, without choosing a subchart value from ambiguous evidence. Include decision 2's NVCRE chart-version and registry-access prerequisites in every printed fallback, with `--version` for dev builds and optional `--chart-ref` for an alternate location. Add the narrow ownership classifier and common failure diagnostics without broadening ADR-073 recovery eligibility or retry count.
- **Cleanup and recovery:** remove automatic JobSet CRD deletion in reset and recovery. Reset keeps the existing exact-release uninstall and Trainer CRD cleanup; JobSet retained-resource lookup failures produce an unverified warning, not a reset failure. Recovery implements decision 4's quiescence prerequisite, post-confirmation gate, workload rechecks before CRD cleanup, and mandatory final namespace inventory. Preserve pre-uninstall evidence for comparison against expected cleanup, use the inspected namespace UID as a delete precondition, and report late refusal as partial recovery. Inventory the protected namespaced resource types before uninstall, excluding Events, core `Endpoints`, and EndpointSlices without listing them or checking their lineage. Apply the manifest/ownership checks, UID owner-reference traversal, and explicit per-kind exceptions in decision 4 to protected resources. Missing required discovery/list permissions or unclassifiable protected resources block recovery with the affected resource, scope, and operation reported. Keep workload blockers independent of inventory exceptions. Make recovery plans, manual guidance, and retained-resource output agree with actual actions.
- **Documentation:** update `docs/cli-reference/setup.md`, `docs/getting-started/install.md`, and `docs/operations/deployment.md` for detection, ambiguous-state refusal, retained CRDs, reset/re-init behavior, and namespace safety, including operator-maintained quiescence, the remaining check-to-delete races, and partial-recovery refusal. Document that existing JobSet CRD schemas are not refreshed by NVCRE, describe the operator-managed upgrade responsibility from decision 3, and name automatic shared-CRD reconciliation as deferred work requiring a separate design. ADR-073 links here as a proposed amendment until this ADR is accepted.

| Plans/docs | Printed recovery and manual procedures omit JobSet CRD deletion, state the quiescence prerequisite even with `--auto-approve`, and respect namespace blockers; `crd-only` reset/re-init reports bundled controller installation using the retained CRD; unknown reports blockers, stops before Helm mutation, and prints manual Trainer installation followed by `nvcrectl setup init --skip-phases=deps`; ambiguous ownership never produces an unconditional recommendation to disable JobSet; each manual fallback states NVCRE chart availability and access requirements, adds `--version` for dev builds, explains optional `--chart-ref` without treating it as a version override, and does not offer current `--skip-phases=deps,helm` as a workaround |

Render the published Trainer 2.2.1 chart with JobSet enabled and disabled to verify resource identities and subchart behavior. Fake-client tests establish decisions and explicit deletion boundaries; they do not establish Helm metadata behavior, Kubernetes namespace garbage collection, or freedom from concurrent writes. Inject changes deterministically at recovery boundaries to verify refusal; passing these cases does not prove quiescence or close the remaining check-to-delete races.

**Automated setup lifecycle UAT is required in the implementation PR.** Add a separate Go test package under `test/uat/setup/`, a `make test-uat-setup` entry point, and a dedicated job in `.github/workflows/uat.yml`. The job builds the current `nvcrectl`, provisions its own disposable Kind cluster with an explicit kubeconfig/context, runs the lifecycle tests, exports CLI and cluster diagnostics on failure, and cleans up the cluster even when tests fail. Use real Helm releases and running controllers. Do not run destructive setup tests against the existing Tilt-managed catalog UAT cluster or simulate controller readiness with KWOK. The existing catalog UAT does not satisfy this requirement because it installs Trainer directly through Helm.

The new suite invokes the built CLI's dependency phase in isolation, and that isolation is a prerequisite the implementation PR must deliver, not something the CLI provides today. Both commands advertise a `helm` phase in their confirmation summary, but nothing reads `skip["helm"]`: the only lookups are `phaseDeps` and `phaseCR`, `installHelmRelease` and `uninstallHelmRelease` run unconditionally, and `parseSkipPhases` accepts any string without validation. `--skip-phases=helm` is therefore silently a no-op that only changes the printed summary. This matters here because a source-built `nvcrectl` carries a `git describe` version, which `resolveHelmChartVersion` rejects as a dev build with no published chart; `[deps]` would complete and then `[helm]` would fail, so every scenario asserting a clean `setup init` would fail on the NVCRE release rather than on anything this ADR covers.

**The implementation PR makes phase selection real.** Promote `helm` to a named phase constant alongside `phaseDeps` and `phaseCR`. On init, skip the complete Helm block containing `setupControllerSecret` and `installHelmRelease`; on reset, skip the complete block containing `uninstallHelmRelease` and the NVCRE `deleteCRDsByGroup` call. Make `parseSkipPhases` reject names outside the command's accepted phase set, so the confirmation summary can no longer misreport what will run. This is a pre-existing defect and is fixed on its own merits; the UAT depends on it. The suite then runs `setup init --skip-phases=helm` and `setup reset --skip-phases=cr,helm`, which exercises only the dependency phase against real Helm releases and a running Trainer controller without packaging an NVCRE chart or installing the NVCRE release. Installing the NVCRE release through `--chart-ref` at a working-tree chart plus `--version` is not required by any scenario below, since all of them assert dependency-phase behavior; it stays available as an option if a future case needs the NVCRE release present, and driving the dependency phase through the package API is rejected because real CLI parsing and phase sequencing are part of what the suite exists to cover.

The suite covers:

- **Bundled upgrade:** seed a real bundled Trainer release with its actual unlabeled JobSet CRD at a chart version that exercises the CLI's upgrade path rather than its pinned-version skip. Run `setup init` and verify the intended upgrade occurred, the JobSet controller remains installed and becomes ready, and the CRD retains its UID. Pin the seed chart version in the test. Note the arm this exercises: a release that is `deployed` at any version other than the pinned one makes `planTrainerPhase` return `trainerActionAttemptRecover`, not `trainerActionInstall`, so the upgrade runs through ADR-073's attempt-then-classify path. That is the intended coverage. A failure in this case must be read against that arm, not as a straight install regression.
- **Bundled reset/init:** with no JobSet instances, run `setup reset` and verify the bundled controller is removed while the CRD retains its UID. Run `setup init` again and verify the bundled controller is installed and ready using that same CRD.
- **External JobSet:** seed a standalone JobSet Helm release in a separate namespace using a pinned chart version. Run `setup init` and `setup reset`; after each command, verify that the external release, controller, and CRD remain, their controller/CRD UIDs and Helm ownership metadata are unchanged, and the external controller is ready. Verify that Trainer installation disabled its JobSet subchart.

Run these destructive scenarios serially with isolated cluster state and bounded readiness waits. Wire the dedicated CI job into the UAT workflow's PR-mirror push, main push, scheduled, and manual triggers. Passing this automated suite is required before the implementation is considered complete; manual testing supplements it rather than replacing it.

## Rationale

- **Controller ownership and CRD creation are different facts.** The actual chart and Helm CRD installation behavior invalidate a CRD-label-only detector. Release/controller evidence protects legacy bundled upgrades; retaining CRDs avoids inventing provenance.
- **An orphaned CRD is safe to install against; a live controller is not safe to disable.** `crd-only` is the one ambiguous-looking state that resolves to action rather than stop, and the asymmetry is deliberate. Installing the bundled controller against a CRD that successful inspection shows has no controller, no supporting resources, no release evidence, and no instances adds a controller where none exists; Helm's `crds/` path skips the existing CRD, so nothing is adopted or overwritten. Disabling the subchart on the same evidence would leave the CRD with nothing reconciling it, which is exactly the silent post-reset failure the original proposal produced. The bar is high on purpose: any leftover supporting resource, conflicting release record, or JobSet without an identifiable controller drops to `unknown`, because then a second controller or an orphaned workload is a real possibility and the operator must decide.
- **Complete release identity prevents cross-namespace adoption.** Helm release names are namespace-scoped even when their resources are cluster-scoped.
- **Ambiguity must not change controller ownership.** Neither enabling a second controller nor removing a bundled one is a safe default after inspection fails.
- **Recovery safety follows all destructive actions.** Release uninstall can remove the controller; namespace deletion can remove foreign resources even when the shared CRD remains.
- **Targeted diagnostics preserve ADR-073.** Ownership errors get useful guidance on first install as well as retry, without widening the conditions that authorize automatic cleanup.

## Consequences

- Clusters with an identifiable external JobSet can install Trainer without manually disabling the subchart. Conflicting or unreadable ownership fails with evidence before mutation.
- Legacy bundled installs remain bundled on upgrades despite unlabeled CRDs.
- Existing JobSet CRD schemas remain unchanged by NVCRE through Trainer upgrades, recovery, and reset/init. A stale schema can prevent newer controller features or workloads from working even after the controller is restored. Operators must manage compatible CRD upgrades and any required migrations; automatic shared-CRD schema reconciliation is explicitly deferred to a separate design.
- Reset and recovery retain JobSet CRDs, including bundled ones. Full removal becomes an explicit operator cleanup step. After reset, init restores the bundled controller when successful inspection establishes the `crd-only` state. Remaining JobSets without an identifiable controller, conflicting resources, or failed inspection require operator reconciliation before installation.
- External JobSets outside the recovery namespace can continue using their external controller while Trainer is recovered, provided the repeated checks find no protected controller or supporting resources in the namespace and the operator maintains decision 4's quiescence boundaries.
- External controller health and version compatibility are not certified by this detector.
- Namespace recovery deletes Events, core `Endpoints`, and EndpointSlices without checking their ownership or lineage. Loss of historical Events and manually managed Endpoints/EndpointSlices is explicitly accepted to keep those objects from preventing recovery. Other unrelated workloads, configuration, and storage block recovery when observed by the repeated inventory checks. Protection depends on operator-maintained quiescence; concurrent writes between inspection and deletion can still be lost.
- A restricted kubeconfig may make automatic recovery unavailable until the operator obtains the required discovery and protected-resource list permissions. Diagnostics identify the missing access; `--auto-approve` cannot bypass it. Events, core `Endpoints`, and EndpointSlices require no list permission for this gate.
- A failed recheck after uninstall can leave Trainer unavailable and its CRDs already removed. Recovery stops with explicit partial-completion diagnostics; it does not roll back completed destructive actions.
- Additional release and Kubernetes reads are required. Inability to obtain required evidence results in a diagnostic refusal rather than an inferred ownership decision.

## Alternatives Considered

- **Install a temporary admission write barrier.** Deferred to a separate design. CRE supports Kubernetes 1.29+, while ValidatingAdmissionPolicy became stable in 1.30. A barrier must cover the affected cluster-wide resources as well as namespace writes, establish enforcement and account for in-flight requests before inventory, define recovery exceptions, and provide additional cluster-scoped RBAC and reliable cleanup after failure. A leaked policy could block legitimate controllers. Automatically quiescing externally owned controllers can disrupt unrelated workloads and is also outside this change.
- **Recover with targeted cleanup that retains the namespace.** Deferred to a separate design validating convergence from the observed partial-install and Secret-conflict states. Retaining the namespace would avoid namespace-wide deletion, but retaining Trainer CRD deletion would still require protection for cluster-wide custom resources.
- **CRD Helm metadata as the sole ownership signal.** Rejected: the published CRD lacks it, and Helm's CRD path does not add it. It would misclassify existing bundled installs.
- **Delete a CRD whenever the controller is bundled.** Rejected: Helm may have reused an existing CRD. Controller ownership does not prove CRD creation or exclusive use.
- **Introduce a new CRD creation marker now.** Deferred: it would need durable, race-safe provenance and migration semantics; it cannot establish ownership retroactively for existing installs. Retention provides the safe behavior for this fix.
- **Automatically reconcile Trainer/JobSet CRDs using the NVCRE `applyChartCRDs` pattern.** Deferred to a separate design: updating a shared JobSet schema requires compatibility and migration rules for external consumers, and bundled controller ownership alone does not authorize that change. Operator-managed schema upgrades are the interim contract.
- **Generic Trainer `--set` / `--values` passthrough.** Outside this change: this design satisfies issue #335's install requirement through automatic detection and the targeted `jobset.install` override. Passthrough alone leaves cleanup ownership and recovery safety unresolved. Operators needing custom values can install Trainer manually and run `nvcrectl setup init --skip-phases=deps`; generic passthrough may be considered in a separate future proposal.
- **Look for a Helm release named `jobset`.** Rejected: external release names and namespaces vary.
- **Always disable JobSet, or use Helm `--take-ownership`.** Rejected: the former breaks bundled lifecycle behavior; the latter adopts resources managed elsewhere.
- **Continue after ownership inspection fails.** Rejected: defaulting the subchart value can either collide with external resources or remove bundled resources.
- **Ignore all external JobSets during recovery.** Rejected: namespace-local instances and controller resources can still be destroyed.

## Notes

- `fullnameOverride: jobset` explains collisions among templated controller/RBAC/webhook resources. Their Helm ownership metadata must not be confused with metadata on the separately installed CRD.
- Trainer 2.2.1 also vendors LeaderWorkerSet (LWS), with a CRD under `charts/lws/crds/`, `dataCache.lws.install: true`, and `dataCache.lws.fullnameOverride: lws`. It is disabled by the default `dataCache.enabled: false`, which NVCRE does not override, so the current setup path has no equivalent LWS ownership collision.
- This ADR remains proposed. Its changes to ADR-073 take effect only after acceptance and implementation.
