# ADR-106: Surface Workload Pods That Are Placed but Never Become Ready

> **Status:** Proposed

## Context

ADR-093 made the MPI worker's readiness probe open a real `ssh` session to the worker itself, so a worker whose `sshd` cannot serve sessions stays `0/1` and the launcher's `dependsOn: [{name: node, status: Ready}]` gate never releases. That moved the failure to where it starts, but it also moved it out of sight. ADR-093's Consequences say so directly: no NVCRE detector reports the state. `checkSchedulingBlocked` acts only on pods the scheduler could not place, and `checkStallTimeout` returns before it looks unless `stallMultiplier` is set, which the communication categories do not set. The Job reports `InProgress=True(WorkloadRunning)` until `timeoutPerJob`, which is 1h for the communication categories (`pkg/catalog/loader.go:67`) and 24h for a WorkloadRun. The diagnosis, `Readiness probe failed:` followed by `ssh`'s own stderr, exists only in `kubectl describe pod` on a worker. Issue #469 tracks relaying it.

The same blind spot covers a pod that is placed and never starts at all. A worker stuck in `ImagePullBackOff`, `CreateContainerConfigError` or a wedged init container is `Pending` with `spec.nodeName` set. The scheduler has done its part, so ADR-083 does not fire, and the Job again waits out `timeoutPerJob` reporting `WorkloadRunning`.

What the controller can see today, and what it cannot:

- **The pod list.** Since ADR-102, `checkSchedulingBlocked` reads `podread.JobPods` (`pkg/controller/job_controller.go:1112`), which answers from the job-label-scoped cache. Only the worker replicatedJob's pod template carries `nvcre.nvidia.com/job` (`InjectPodLabel` at `pkg/workload/trainjob.go:61`; `workerTargetJob` skips the launcher), and `pkg/podread/podread.go:180` states it outright: launchers carry no job label, so the cache cannot hold them. Any rule that reads "the launcher does not exist" off that list is always true, silently.
- **The pod's own status.** For a `Running` pod that fails its readiness probe, the kubelet sets `ContainersReady=False` with reason `ContainersNotReady` and the message `containers with unready status: [node]`. That names the container and nothing else. For a `Pending` pod, `status.containerStatuses[].state.waiting` (and `status.initContainerStatuses[]`) carry the kubelet's reason and message, for example `ImagePullBackOff` with the pull error.
- **Events.** The probe output lives only in the `Unhealthy` Event the prober emits for the pod (`Readiness probe failed: ...`). Nothing in the controller reads Events today. ADR-083 dropped its Event read in review because the pod condition carried the same text without it; here the condition does not.

## Decision

Add a second detector on the Job tier, next to the ADR-083 scheduling-stall detector, that reports workload pods which were placed but never became Ready. It reuses ADR-083's grace field, Workflow reason and report line, and it keeps `timeoutPerJob` running.

1. **Detection: a placed pod that is stuck, not one that is still starting.** The detector runs on the running path, on the same `podread.JobPods` list `checkSchedulingBlocked` already read. A pod is a candidate when all of these hold:
   - `spec.nodeName` is set;
   - its phase is `Pending` or `Running`, so a `Succeeded` or `Failed` pod, whose `ContainersReady` is also `False`, never counts;
   - it has no `deletionTimestamp`;
   - it carries `ContainersReady=False`.

   A candidate is still starting, and does not count, while none of its init containers or containers is running and each one that is waiting has reason `ContainerCreating` or `PodInitializing`, or no reason. Those are the reasons the kubelet reports while it pulls images and sets up the sandbox and volumes (`PodInitializing` and `ContainerCreating` in upstream `pkg/kubelet/kubelet_pods.go`). This matters because `TrainJobAdapter.GetStatus` reports `WorkloadRunning` as soon as the TrainJob is not suspended, before any pod exists (`pkg/workload/trainjob.go:197-209`), so without the rule a slow first image pull would sit inside the grace window and come out the other side as an episode. A candidate counts in one of two ways:
   - **Stuck waiting:** an init container or container is waiting with any other reason, for example `ErrImagePull`, `ImagePullBackOff`, `InvalidImageName`, `CreateContainerConfigError`, `CreateContainerError` or `CrashLoopBackOff`. These are failures the kubelet is retrying, not progress.
   - **Started but not Ready:** an init container, or a container that is not ready, is running. Its time is measured from its own `state.running.startedAt`, so each pod's window opens when its own process starts, not when the first pod of the gang did.

   The state fires when a pod has been started but not Ready for longer than the grace window of decision 4, measured from that `startedAt`, or when a pod is stuck waiting and the episode (`workloadPodsNotReadySince`, decision 6) has lasted longer than the grace window. There is no launcher gate. The list is worker-only, so a launcher gate read from it is always open, and the gate is not what keeps the detector from firing mid-run anyway: a healthy worker is Ready while the workload runs. A worker that turns NotReady mid-run and stays that way past grace is reported, which is the truth. Widening from `Running` to `Pending or Running` costs nothing extra (it is the same list, and the waiting reasons, start times and `Pending` message are on the pod), and it closes the `ImagePullBackOff` and wedged-init gap above, so it is in scope.

2. **Precedence: ADR-083 first.** The not-ready check runs only after `checkSchedulingBlocked` returns not blocked and no scheduling-blocked episode is open. A workload with both unscheduled and placed-but-unready pods reports `WorkloadSchedulingBlocked`, and its clock stays paused, as ADR-083 decides.

3. **The message comes from the `Unhealthy` Event; the pod is the fallback.** The detector picks one pod, the first not-Ready pod by name so the choice is stable across reconciles, and relays one line for it:
   - **`Running` pod:** the newest `Unhealthy` Event for that pod. If there is none (Events expire, and a container in `CrashLoopBackOff` may never be probed), the first container's `state.waiting` reason and message, then the `ContainersReady` condition message as the last resort.
   - **`Pending` pod:** the first waiting init container's `state.waiting`, then the first waiting container's, as `<container>: <reason>: <message>`. No Event read.

   The order is the reverse of ADR-083's, for the reason ADR-083 gives: there kube-scheduler writes its own diagnosis into `PodScheduled`, so the condition is the better source; here the kubelet writes only the container name into `ContainersReady`, and the probe output is in the Event.

   **The Event read is live, once per episode, and scoped to one pod.** It goes through `r.APIReader` as a `corev1.EventList` in the Job's namespace with field selectors `involvedObject.name=<pod>` and `reason=Unhealthy`, and keeps only Events whose `involvedObject.uid` is the pod's UID, so an Event left by a deleted pod of the same name is never relayed. The newest wins by `series.lastObservedTime`, then `lastTimestamp`, then `eventTime`. It is read only on the reconcile that is about to raise the reason. `podsNotReadyMessage` is pure and `setJobInProgress` passes its message straight to `setExclusiveCondition` (`pkg/controller/job_controller.go:1494`), so keeping the text is the running branch's job: when the `InProgress` condition already carries `WorkloadPodsNotReady` for the same chosen pod and that pod is still `Running`, the branch reuses the relayed text from the existing condition message instead of reading Events again, and recomputes only the `(<n> of <m> pods not Ready)` suffix, which the controller wrote itself. A different chosen pod, or the chosen pod leaving `Running`, recomputes the message, with a fresh Event read only if the new pod is `Running`. A `Pending` pod's text comes from its own fields and is recomputed every reconcile, as ADR-083's `blockMsg` is (`job_controller.go:873`), because it is stable. It must not be a cached read: a cached Event read starts a cluster-wide informer that needs `list` and `watch` in every namespace, which loops on forbidden under `rbac.scope: namespaced` (issue #424), and it is why `ClientOptions` (`pkg/controller/cache.go:378`) keeps ConfigMaps and PVCs out of the cache. A failed read is logged and falls through to the pod's own fields, so a missing permission degrades the message, never the detection.

   The relayed text is capped at 1 KiB, cut on a UTF-8 boundary with a trailing `...`, because the Workflow appends it to its own condition message and the report prints it. The Job condition message is `Workload pods are not Ready: pod <pod>: <text>`, and adds `(<n> of <m> pods not Ready)` when more than one pod matches.

4. **Grace: reuse `schedulingStallGraceSeconds`, and widen it wherever the worker installs `sshd`.** It sits on `JobSpec` (`api/v1alpha1/job_types.go:297`), and a catalog entry's `jobTemplate.spec` is a `JobSpec`, so a category whose image installs `sshd` at start can widen it without a new knob. The default stays 5 minutes (`defaultSchedulingStallGrace`, `pkg/controller/job_controller.go:79`). That covers one install attempt, which `sshdInstallCommand` bounds at 4 minutes, but not the retry path: the budget is 4 minutes for the first attempt and 6 for each retry, 16 in all (`pkg/platform/runtime.go:405`), and `docs/operations/troubleshooting.md:193` says a failed attempt followed by a successful one needs no action. So every Job whose worker runs `sshdInstallCommand` sets `schedulingStallGraceSeconds: 1020`, the 16 minute budget plus one 30s probe period and a margin:
   - the three entries that render `_lib/nccl/mpi-worker-sshd-args.yaml`: `nccl-all-gather`, `nccl-all-reduce` and `nccl-alltoall`, in their `jobTemplate.spec`;
   - a WorkloadRun whose runtime comes from `platform.BuildMPIRuntime`, on the `JobSpec` built for it. There are two builders, and both take that branch. The controller's `buildJobTemplate` (`pkg/controller/workloadrun_controller.go:680`, runtime at `:572`, `JobSpec` at `:747`) builds the Job a WorkloadRun creates. `buildCLIJobTemplate` (`pkg/workloadrun/workloadrun.go:494`, runtime at `:352`, `JobSpec` at `:557`) assembles its own `JobSpec` and says it mirrors the controller's builder; it is what `BuildWorkflowSpec` uses for `nvcrectl workloadrun render` (`runWorkloadRunRender`, `:203`) and the dry run (`runWorkloadRunRenderDryRun`, `:690`). Setting the field in only one of them would make `nvcrectl workloadrun render` print an MPI Workflow without the grace the controller sets, or the reverse. Both read the value from one constant next to `sshdInstallCommand` in `pkg/platform`, so the number cannot drift between them.

   A check next to `TestSSHDWorkerInvariants` fails for a worker that runs `sshdInstallCommand` in a catalog entry whose `jobTemplate.spec` has a smaller grace, so a new catalog entry cannot ship without it. The check does not reach either Go builder: its builder cases drive `BuildMPIRuntime` directly (`pkg/platform/sshd_worker_invariants_test.go:215`) and get back a runtime `DependencySpec`, never a `JobSpec`. The two builders are pinned by their own tests instead (Testing plan), and a third Go builder that assembles a `JobSpec` for an `sshd` worker would not be caught by the check. Past 1020s the install has either finished or ended in `exit 1`, so a worker that is still not Ready is one the detector should report. Because the window is measured per pod from its container's start (decision 1), pulls that finish at different times on different nodes do not eat into it. The field's doc changes from "unschedulable" to "blocked: unschedulable, or placed but not Ready", and it says the two cases differ in clock accounting (decision 5).

5. **`timeoutPerJob` keeps running, and the start time is stamped in the same write.** Unlike a scheduling block, the nodes are held and the fault is inside the workload, so the time counts. But counting has to be enforced at the write, not inherited. The ADR-083 path returns at `job_controller.go:879`, before the status write that stamps `workloadStartTime` at `:928`. A not-ready path with the same shape would leave a Job that is not Ready on its first running-path observation with a `WorkloadRef` and no start time, which `isJobTimedOut` (`pkg/controller/workflow_controller.go:1266`) reads as not started and never times out. "Count it" would become "never terminates". So there is one write: the running branch picks the reason, `WorkloadPodsNotReady` past grace and `WorkloadRunning` otherwise, and passes it to the same `setJobInProgress` call that stamps `workloadStartTime` and sets or clears the episode marker. `isJobTimedOut` then needs no change, and a unit case pins that a Job whose first observation is already not Ready gets its start time in that write. Stall detection runs exactly as it does now, before the write.

6. **Restart safety: `status.workloadPodsNotReadySince`.** An episode starts at the first observation of a pod that counts under decision 1 or has a running container that is not Ready; a pod that is still starting opens none. The first observation of an episode records it, in the same write as decision 5. A successful list that finds no not-Ready pod clears it and returns the reason to `WorkloadRunning`; a failed list changes nothing, so a transient error cannot reset grace. A checkpoint restart clears it with `workloadStartTime`. A terminal Job keeps it, as it keeps `schedulingBlockedSince`, so the Workflow's timeout path can say why: a Job that times out with the marker set fails with `Job exceeded timeoutPerJob while its pods were not Ready`. Unlike the scheduling-blocked case, its nodes are still attributed in `failedNodes`, since the pods were placed and held them (ADR-099).

7. **Surfacing reuses ADR-083's Workflow reason, so the report does not change.**
   - **Job:** `InProgress=True(WorkloadPodsNotReady)` with the message of decision 3, and one Warning Event `WorkloadPodsNotReady` on the Job when the reason is entered. A reason change inside `InProgress` raises no transition Event on its own (`setExclusiveStatusConditionUnless` reports type changes only), so the detector emits it.
   - **Workflow:** no new reason. `schedulingBlockedMessage` (`workflow_controller.go:1303`) gains a case returning `job <name> pods not ready: <Job message>`, and the running-group loop already raises `ReasonJobSchedulingBlocked` with that text. That reason already relays a cause that is not scheduling (`WorkloadCreationRejected`, issue #488).
   - **Report:** `runningStatusDetail` prints the Workflow message only for reasons in `blockedReasons` (`pkg/report/report.go:590`), and `JobSchedulingBlocked` is already there. The `Blocked:` line shows the new text with no report change. A new Workflow reason would have needed one.

8. **The reason is `WorkloadPodsNotReady`.** The detector observes any job-labelled pod that was placed and did not become Ready, not an MPI role, so `WorkloadWorkersNotReady` would name the wrong thing.

## Implementation

- **`api/v1alpha1/job_types.go`**: `status.workloadPodsNotReadySince` (`*metav1.Time`, optional), and the widened doc on `spec.schedulingStallGraceSeconds`. `make manifests` regenerates the CRD.
- **`pkg/controller/helpers.go`**: `ReasonWorkloadPodsNotReady` on the Job tier, documented as counting against `timeoutPerJob`, unlike `ReasonWorkloadSchedulingBlocked`.
- **`pkg/controller/job_controller.go`**
  - `checkPodsNotReady(ctx, job, pods)` takes the list `checkSchedulingBlocked` read, so a reconcile still makes one cached pod list. `checkSchedulingBlocked` returns that list alongside its result. The function applies decision 1 and returns the not-Ready pods; it writes nothing.
  - `podsNotReadyMessage(pod, events)`, a pure function that applies decision 3's order and the 1 KiB cap. The Event read sits in a small `unhealthyEvents(ctx, pod)` helper over `r.APIReader`. The reuse rule of decision 3 sits in the running branch, which reads the kept text off the existing `InProgress` condition and skips the Event read when it applies.
  - In the `default` (running) branch, after the stall check: the final `setJobInProgress` takes its reason and message from the not-ready result, and one extra mutation sets or clears `workloadPodsNotReadySince` next to the existing `workloadStartTime` stamp. The Warning Event is emitted when the reason moves to `WorkloadPodsNotReady`.
  - `restartFromCheckpoint` clears the marker with `workloadStartTime`.
  - `+kubebuilder:rbac:groups="",resources=events,verbs=list`, for the record only.
- **`helm/cluster-readiness-engine/templates/run-role.yaml`**: a rule granting `list` on `events` in the core group, next to the `pods/log` read. Only `list`: decision 3 reads a field-selected `EventList` and never reads an Event by name, so `get` would go unused. Added by hand: `make manifests` writes no RBAC (ADR-092). ADR-092 put the controller's other read of workload content, pod logs, in `nvcre-run-role`, so this grant follows `rbac.scope` the same way: cluster-wide under `cluster`, and only in bound namespaces under `namespaced`. The Job is created in its Workflow's namespace, which that binding already covers. `nvcre-manager-role` is unchanged: it is bound cluster-wide under both scopes, and binding it per namespace would break its cluster-scoped grants. The namespace access check (`pkg/controller/namespace_access.go`) does not gain the verb, because the read is best effort (decision 3): a narrower custom Role without it degrades the message and does not hold the Workflow. This is the first `list` verb `nvcre-run-role` carries, against ADR-092's choice to drop `list` from it. It is acceptable because the read goes through `r.APIReader`: it is uncached, so it starts no informer, needs no `watch` and does not reopen #424, and each call is one namespaced list filtered to one pod. The same change updates every place that says otherwise: the template's header comment (`run-role.yaml:11`, "None of these resources is listed"), the `rbac:` preamble in `helm/cluster-readiness-engine/values.yaml:57` (events stay in `nvcre-manager-role` only for the recorder's `create` and `patch`), ADR-092's role table and its "`list` is dropped" bullet (092:78), ADR-000's Controller Patterns paragraph, and the RBAC pitfall in `AGENTS.md` and `CLAUDE.md`. Two places in ADR-092 enumerate the role split's intended differences and are amended to name this one as a later, deliberate addition: 092:81, which says the `list` removals, the ConfigMap `list` and `watch` removal and the Namespace `get` and SelfSubjectAccessReview `create` additions "are the only intended differences from today's rule set", and 092:134, which says the `test/helm/` golden "records exactly the differences listed under Role split". The helm RBAC goldens under `test/helm/` change with the rule: in `test/helm/testdata/role-split/cluster-mode-union/expected.json`, the `added` array gains `list events` and becomes `["list events", "get namespaces", "create selfsubjectaccessreviews.authorization.k8s.io"]` (`sortedDifference` orders by resource, then verb), and the `runRole` array gains `list events`. `managerRole` and `removed` do not change. The `run-namespace-access` golden does not change, since the namespace access check does not gain the verb.
- **`sshd` grace (decision 4)**: `schedulingStallGraceSeconds: 1020` in the `jobTemplate.spec` of `pkg/catalog/entries/communication/nccl-all-gather.yaml`, `nccl-all-reduce.yaml` and `nccl-alltoall.yaml`, and on the `JobSpec` built for a `BuildMPIRuntime` runtime by both `buildJobTemplate` in `pkg/controller/workloadrun_controller.go` and `buildCLIJobTemplate` in `pkg/workloadrun/workloadrun.go`, from one constant in `pkg/platform`; the catalog invariant check next to `TestSSHDWorkerInvariants` in `pkg/platform/sshd_worker_invariants_test.go`. Goldens that render those entries gain the field, and so do the MPI goldens of both builders: the `pkg/workloadrun/testdata/build-workflow-spec/` cases for an MPI run, and the MPI WorkloadRun cases under `cmd/integration/testdata/reconcile/` (`workloadrun-mpi` and the others whose `jobTemplate` comes from `BuildMPIRuntime`).
- **`pkg/controller/workflow_controller.go`**: the `ReasonWorkloadPodsNotReady` case in `schedulingBlockedMessage`; the not-Ready timeout message in the timeout path. `isJobTimedOut` is unchanged.
- **`cmd/integration/integration_test.go`**: normalize `workloadPodsNotReadySince` to the fixed placeholder, the way `schedulingBlockedSince` is at line 1727, or every golden that carries it flakes.
- **Docs**: `docs/api-reference/job.md`, `docs/operations/troubleshooting.md` and `docs/concepts/health-monitoring-remediation.md` gain `WorkloadPodsNotReady` where they describe `WorkloadSchedulingBlocked`; ADR-093's Consequences point here; `CHANGELOG.md` gets an `[Unreleased]` entry.
- **API cost:** no new cached read. One live, namespaced, field-selected Event list per not-Ready episode, only for a `Running` pod.

### Testing plan

No GPUs are needed.

- **Message projection, as `testutil` goldens** under `pkg/controller/testdata/pods-not-ready-message/`, the shape of `not-enough-nodes-message` and `gpu-arch-fallback-message`. Cases: a `Running` pod with an `Unhealthy` Event; several Events, newest wins; an Event whose UID belongs to a deleted pod of the same name, ignored; no Event, falling back to `state.waiting` and then to the condition; a `Pending` pod in `ImagePullBackOff`; a wedged init container; several not-Ready pods; text over 1 KiB, cut on a rune boundary.
- **Tables for the nil-safety and classification pins**, next to `scheduling_stall_test.go`: no conditions, no container statuses, a `Succeeded` pod, a terminating pod, an unplaced pod (ADR-083's), a Ready pod. For decision 1: a `Pending` pod waiting in `ContainerCreating` or `PodInitializing`, not counted however long ago the TrainJob started; `ErrImagePull` and `ImagePullBackOff`, counted; a running container that is not ready, counted only once its `startedAt` is older than grace; two pods whose containers started minutes apart, where only the older one counts.
- **Reconcile cases**: inside grace (marker set, reason `WorkloadRunning`) and past grace (reason `WorkloadPodsNotReady`, one Warning Event); recovery clearing the marker; a scheduling block taking precedence; a failed pod list leaving the marker alone; a failed Event read falling back to the pod. **The decision 3 keep rule:** the reconcile that raises the reason relays the probe text from an Event, and a second reconcile with no Event in the live fake client keeps that text; a second reconcile whose chosen pod changed reads Events again. **Decision 4:** a 1020s grace keeps a worker that is not Ready for 16 minutes at `WorkloadRunning`. Because the catalog invariant check cannot see a Go-built `JobSpec`, each builder has its own pin: an MPI case in `build-workflow-spec` and an MPI WorkloadRun reconcile golden both carry `schedulingStallGraceSeconds: 1020`, and a Torch case of each carries no field. **The decision 5 pin:** a Job whose first running-path observation is already not Ready has `workloadStartTime` set in the same write as the reason, and `isJobTimedOut` times it out once `timeoutPerJob` passes. The Event read is pinned to `APIReader` by putting the Event only in the live fake client.
- **Workflow**: `schedulingBlockedMessage` returns `job <name> pods not ready: ...` for the new reason, and a timed-out Job with the marker set carries the not-Ready timeout message and its nodes in `failedNodes`.
- **Integration**, under `cmd/integration/testdata/reconcile/`: `job-pods-not-ready`, with job-labelled worker pods that are placed, `Running` and `ContainersReady=False`, an `Unhealthy` Event for one of them, and no launcher; and `job-pods-not-ready-image-pull`, with a placed `Pending` worker in `ImagePullBackOff`. As ADR-102 requires, any launcher pod in a fixture carries no job label. The harness's refused-read check must stay clean, which also shows the Event read did not go through the cache.

## Rationale

- **Why the Event, when ADR-083 rejected Events?** ADR-083 rejected them because the pod condition held the same diagnosis without a read. Here it does not: the only place the probe output exists is the `Unhealthy` Event. The costs ADR-083 named are each answered: the read is live and namespaced (no informer, no #424 loop), one per episode (not per reconcile), and filtered by UID (no relay from a deleted pod of the same name).
- **Why widen detection?** The widened predicate is the same loop over the same list, and the `Pending` message is on the pod, so it adds no read. Leaving it out would leave `ImagePullBackOff` and wedged init containers waiting out `timeoutPerJob` as `WorkloadRunning`, and nothing else catches them. The kubelet's own waiting reasons are what separate starting from stuck: `ContainerCreating` and `PodInitializing` are progress, the others are retries of a failure, so a long pull is not reported and a failed one is.
- **Why widen the grace per Job rather than change the default?** Only Jobs that run `sshdInstallCommand` need 17 minutes. A 17 minute default would make every image that ships `sshd`, and every ADR-083 scheduling report, wait that long too.
- **Why reuse `ReasonJobSchedulingBlocked`?** It keeps the report change at zero, and the reason already relays a cause that is not scheduling. Its Go name is narrower than its use, which is a naming cost; a rename touches the API's reason vocabulary and is not worth doing here.
- **Why count the time?** The resources are held and the fault is inside the workload. Pausing the clock would let a pod that can never become Ready hold GPUs for longer than the operator's budget. This state makes the wait visible; it does not change how long it may last.
- **Why one write?** Two writes on the running path is the bug decision 5 describes. One write cannot stamp the reason without the start time.

## Consequences

- A worker whose `sshd` refuses sessions, or any placed pod that never becomes Ready, shows as `InProgress=True(WorkloadPodsNotReady)` with the probe's or the kubelet's own text on the Job, as `JobSchedulingBlocked` with `job <name> pods not ready: ...` on the Workflow, and on the report's `Blocked:` line, within one reconcile of grace elapsing, instead of never.
- `timeoutPerJob` is unchanged in effect: the Job still times out when it would have, now with a message that says why.
- The controller reads Events for the first time, and `nvcre-run-role` gains `list` on core `events`. Under `rbac.scope: cluster` that exposes Event contents in every namespace to the controller's service account, as pod logs already are; under `namespaced`, only in the namespaces it is bound in. The read itself is confined to the Job's namespace and one pod.
- A new optional status field, `workloadPodsNotReadySince`. No new spec field, no new Workflow reason, no report change.
- `schedulingStallGraceSeconds` now also delays this condition. A site that set it high to tolerate slow scheduling also waits longer to see a not-Ready pod reported.
- The reverse holds for the Jobs decision 4 widens: on `nccl-all-gather`, `nccl-all-reduce`, `nccl-alltoall` and MPI WorkloadRuns, whether the controller builds the Job or `nvcrectl workloadrun render` prints it, an unschedulable workload is reported after 17 minutes instead of 5. ADR-083 pauses the clock from the first observation, so no budget is lost, only the earlier report. If that delay proves to matter, the separate grace field under Alternatives is the way out.
- A genuine `sshd` failure on those Jobs is reported after 17 minutes, on a 1h `timeoutPerJob`, instead of never.
- Adapters are unchanged.

## Alternatives Considered

- **Keep the launcher-absent gate.** Rejected. Read from the cached list it is always true; read correctly it needs a live `podread.WorkloadPods(ctx, ns, workload, "launcher")` on every running reconcile, to guard against a case the Ready check already rules out.
- **The `ContainersReady` condition as the primary message.** Rejected: for a probe failure it names the container and nothing else.
- **A cached Event read.** Rejected: cluster-wide informer, `list` and `watch` in every namespace, and the #424 forbidden loop under `rbac.scope: namespaced`.
- **A new Workflow reason.** Rejected: invisible in the report until it is added to `blockedReasons`, for no gain over a `schedulingBlockedMessage` case.
- **A separate `workersNotReadyGraceSeconds`.** Not taken. The existing field is on `JobSpec` and already reachable from the catalog. Splitting it would keep decision 4's wider window off ADR-083's report, at the cost of a new API field; it can be done later if the 17 minute scheduling report proves to matter.
- **A 17 minute default.** Rejected: it delays both reports on every Job, including those whose image ships `sshd` and never runs the install.
- **Exclude the install phase.** Not taken. The install runs in the worker's main container before `sshd` starts, so nothing on the pod tells it apart from an `sshd` that cannot serve sessions. Moving it to an init container would change the worker layout ADR-093 and `TestSSHDWorkerInvariants` pin, and a running init container still counts under decision 1.
- **Pause `timeoutPerJob` while not Ready.** Rejected; see Rationale.
- **`Running` pods only.** Rejected once widening proved to cost nothing; see decision 1.

## Notes

- The probe itself is out of scope; it is ADR-093's.
- The `--wait` stream still shows only category status, the gap ADR-083 decision 7 already tracks.
- A pod that stays in `ContainerCreating`, for example on a volume that never mounts or a pull that hangs without an error, counts as still starting and waits out `timeoutPerJob` as it does today. Its cause is in `FailedMount` or pull Events, which a later change could relay the same way.
- A pod that keeps restarting and passes its probe between crashes can flip in and out of the state. Grace filters the flapping, and the restart count is already in the pod. A restart-count detector would be its own change.
