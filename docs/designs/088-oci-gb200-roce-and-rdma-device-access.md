# ADR-088: OCI GB200 RoCE Overrides, and `rdmaDeviceAccess` for hostPath RDMA

> **Status:** Accepted

## Context

A user certifying an OCI GB200 cluster (GitHub issues #456 and #350) cannot get a catalog NCCL category to run. Two separate things are wrong, and fixing either one alone leaves the cluster uncertifiable.

**1. OCI GB200 renders none of the OCI RoCE environment.** Rendering a Certification with `communication/nccl-all-reduce`, `communication/nccl-loopback` and `training/nemotron5-8b` against `--platform oci` emits, for GB200, exactly two RoCE-relevant variables: `NCCL_IB_TIMEOUT` and `NCCL_SOCKET_IFNAME`. Both come from `_lib/nccl/gb200-training-base-env.yaml`, inlined in the `nemotron5-8b` TrainingRuntime (`pkg/catalog/entries/training/nemotron5-8b.yaml:146`). No OCI fragment contributes anything. The same render against GB300 emits 24 occurrences of 11 distinct variables, including `NCCL_IB_GID_INDEX`, `NCCL_IB_TC`, `NCCL_IB_SL`, `NCCL_IB_QPS_PER_CONNECTION` and `UCX_IB_GID_INDEX`.

   OCI is RoCEv2, and `_lib/nccl/oci-roce-env.yaml` exists precisely to carry that: GID index 3, traffic class 41, service level 0, four QPs per connection, PCI relaxed ordering, `NCCL_SOCKET_IFNAME=eth0`. Without GID index 3, UCX and NCCL default to GID index 0, which is link-local, and the RDMA connection fails with `IBV_WC_REM_ACCESS_ERR` (the mechanism is already documented in `_lib/nccl/oci-gb300-roce-env.yaml:6-11`).

   Two distinct root causes produce the gap, and they need different fixes:

   - **The five communication entries lose it to override ordering.** Each has a `platform: oci` block that sets `trainer.args` from `oci-roce-env.yaml | toMpiArgs` (or `trainer.env`, for the two loopback variants). A later `gpuArchitecture in [gb200, gb300]` block then sets the same field. Overrides apply in document order with no specificity ranking (`applyOverrides`, `pkg/controller/workflow_detect.go:526`), `trainer.args` is an unnamed list so it replaces atomically, and `trainer.env` replaces atomically too because Kubeflow's `Trainer.Env` carries no `patchMergeKey` struct tags. `mergeJobTemplate`'s own doc comment records this (`pkg/controller/workflow_detect.go:610-614`). The later block wins and the OCI environment is discarded. GB300 escapes because it has its own `platform: oci` + `gpuArchitecture: gb300` block placed after the architecture block; GB200 has no such block.

   - **The two training entries never had an arm.** `nemotron5-8b.yaml:295-303` and `nemotron5-56b.yaml:267-275` match `gpuArchitecture in [gb200, gb300]` but set only `dependencies` and `orchestration.topology.topologyKey`; they touch no `jobTemplate`. Nothing is clobbered. Their `platform: oci` arm is scoped `gpuArchitecture in [l40, l40s]`, and their OCI arm for GB300 is scoped `equals: gb300`. OCI GB200 matches neither, so the arm is simply missing.

**2. There is no way to reach the RDMA devices without an SR-IOV device plugin.** The reporting cluster exposes Mellanox devices to pods by hostPath-mounting `/dev/infiniband`. It runs no SR-IOV device plugin, advertises no `nvidia.com/mlnxnics`, and has no `sriov-net` NetworkAttachmentDefinition. ADR-087 made that cluster schedulable by defaulting OCI GB200 to `mlnxPerNode: 0`, so pods no longer stay Pending. It did not give them device access: the catalog grants the worker container only `IPC_LOCK` (`nccl-all-reduce.yaml:56-59`), and nothing in the catalog mounts `/dev/infiniband` on any platform.

   The user ran the experiment that settles what is required. A nonprivileged pod with `IPC_LOCK` and the same hostPath mounts could see `/dev/infiniband/uverbs0` but `open()` returned `Operation not permitted`. Two privileged pods with the same mounts completed `ib_write_bw` over `mlx5_0` at 387.18 Gb/s average. That result is not specific to their cluster: kubelet builds the container's device cgroup allowlist from the container's *requested resources*, so a hostPath mount of a device tree grants a path and no permission. Only a device-plugin resource request or `privileged: true` changes the cgroup. No capability, `IPC_LOCK` or otherwise, substitutes.

   So the catalog supports exactly one RDMA access model, the device-plugin one, and the cluster in the report runs the other.

**3. The repository has no position on container privilege.** There is no ADR on privilege, capabilities, device cgroups, or Pod Security Standards, and no PSS enforcement in `pkg/controller/`, `pkg/setup/` or `helm/`. The two nearest facts point in opposite directions, and both have to be addressed rather than cited selectively:

   - `diagnostics/dcgm-level4.yaml:37` sets `privileged: true` unconditionally in the base, and its `platform: oci` override at `:88-111` sets `privileged: false` under the comment "CRI-O rejects privileged containers with device plugin GPU injection (device paths already exist on host)". OCI is the one platform where this repository already records that privileged does not work. That text dates to the initial commit (`908cb14c`) with no ADR behind it.
   - ADR-016:58 states the opposite preference for volumes: "**emptyDir for dshm** (not hostPath): More portable across environments... without requiring host access."

   The only hostPath precedent in the catalog is `_lib/deps/gcp-h100-tcpxo-runtime-patch.yaml:71-82`, which mounts `/home/kubernetes/bin/nvidia`, `/sys`, `/proc/sys` and `/dev/aperture_devices`, and adds `NET_ADMIN` and `NET_BIND_SERVICE` to the `tcpxo-daemon` init container. It is unconditional within the GCP H100 branch, not opt-in.

   Note that CLAUDE.md:251, `docs/concepts/platform-detection.md:78` and `docs/how-to-guides/certify-a-cluster.md:39` all described an EFA hostPath volume for AWS GB200 (`CLAUDE.md` named it `amazon-efa`). No such volume exists in any catalog entry, and `test/uat/testdata/aws/gb200/nccl/expected_pods.yaml` has zero hostPath entries. This change removes the claim from all three; it was never precedent and is not cited as such here.

Defect 1 is what makes the certification produce wrong results. Defect 2 is what makes it not run at all on the reported cluster. Both have to land for "certification runs on OCI GB200" to be true.

## Decision

1. **Add an OCI + GB200 override arm to each of the seven affected entries**, placed after the `gpuArchitecture in [gb200, gb300]` block so its `trainer.args` / `trainer.env` replacement wins. The arm composes the existing OCI RoCE environment with the existing GB200 environment, rather than inventing either.

2. **Add one shared fragment, `_lib/nccl/oci-gb200-roce-env.yaml`**, carrying `UCX_IB_GID_INDEX=3` and nothing else. It is a delta over `oci-roce-env.yaml`, which already carries `NCCL_IB_GID_INDEX=3`, and is always included after it rather than instead of it. GB300's extra tuning (`NCCL_DMABUF_ENABLE=0`, `NCCL_IB_ADAPTIVE_ROUTING=1`, `NCCL_IB_SPLIT_DATA_ON_QPS=1`) stays GB300-only: each of those is a recorded GB300 hardware finding, not a platform fact.

   The delta shape is forced, not stylistic. The Workflow CRD declares `spec.jobTemplate.spec.workload.trainJob.trainer.env` a server-side map list keyed on `name` (`x-kubernetes-list-type: map`, `helm/cluster-readiness-engine/crds/nvcre.nvidia.com_workflows.yaml:6789-6791`), so a second entry for a name the base fragment already set makes the API server reject the whole Workflow with `Duplicate value`. A fragment that repeated `NCCL_IB_GID_INDEX` for self-sufficiency would be legal in `trainer.args`, where `mpirun -x` simply takes the last value, and fatal in `trainer.env`. One shape that works in both is worth more than self-sufficiency.

3. **Add an opt-in `rdmaDeviceAccess` enum to `CategoryOptions`** with values `hostPath` and `devicePlugin`. Unset keeps today's behavior exactly. `devicePlugin` names today's behavior explicitly and renders nothing extra. `hostPath` mounts the host's `/dev/infiniband` into the worker container and sets `privileged: true` on that container, and nothing else.

4. **Mount `/dev/infiniband` and nothing else.** Not `/sys/class/infiniband`, not `/sys/bus/pci`, not `/proc`. The device nodes are the only thing the container cannot already reach: `/sys` is mounted read-only in every container by the runtime, so `/sys/class/infiniband` is already present. This is the smallest host surface the reported experiment proves is needed.

5. **Do not add a generic per-category `env` map.** The user's four named variables (`NCCL_IB_GID_INDEX`, `NCCL_IB_TC`, `NCCL_SOCKET_IFNAME`, `NCCL_IB_HCA`) are answered by decision 1: the first three are in `oci-roce-env.yaml` already and start reaching GB200, and `NCCL_IB_HCA` is deliberately unpinned so NCCL auto-detects. A general env-injection surface is a larger API question than this report needs.

6. **Do not change `diagnostics/dcgm-level4.yaml`.** It is not an RDMA workload, it does not consume the new fragment, and its OCI `privileged: false` arm stays as it is.

### Where the new arms go, and what each one sets

Placement is not stylistic. Overrides apply in document order and the later match wins on any field it sets, so each arm must come after the `gpuArchitecture in [gb200, gb300]` block in its file.

| Entry | Base arm shape | New OCI + GB200 arm |
|---|---|---|
| `communication/nccl-all-reduce`, `nccl-all-gather`, `nccl-alltoall` | MPI; arch block replaces `trainer.args` | `trainer.args` = `oci-roce-mpirun-args.yaml` + `oci-roce-env.yaml \| toMpiArgs` + `gb200-env.yaml \| toMpiArgs` + `oci-gb200-roce-env.yaml \| toMpiArgs` + the perf binary + `nccl-perf-args.yaml`; `trainer.env` = `oci-roce-env.yaml` + `oci-gb200-roce-env.yaml` |
| `communication/nccl-loopback`, `nccl-loopback-nvswitch` | torch, single node; arch block replaces `trainer.env` | `jobTemplatePatch` appending `UCX_IB_GID_INDEX` and `NCCL_IB_GID_INDEX`, mirroring each file's existing GB300 arm line for line |
| `training/nemotron5-8b`, `nemotron5-56b` | torch; arch block sets no `jobTemplate` at all | `trainer.env` = `oci-roce-env.yaml` + `oci-gb200-roce-env.yaml` |

Three details follow from the merge machinery rather than from preference:

- **The MPI arms need `trainer.env` as well as `trainer.args`.** `mpirun -x` propagates to the ranks on the worker pods, but the launcher container runs its own MPI initialization from its own container environment. The GID variables have to be in `trainer.env` for the launcher to pick them up. `trainer.env` does reach the launcher: the launcher's replicatedJob carries `trainer.kubeflow.org/trainjob-ancestor-step: trainer` (`nccl-all-reduce.yaml:71-73`), and Kubeflow applies `Trainer.Env` to the container named `node` inside that pod set (`jobset/builder.go:142-166`). The launcher runs no rank of its own, since `runLauncherAsNode` defaults false and the hostfile lists only the node pod set (`mpi.go:297-309`, `:325-327`); the existing comments calling it "rank 0" are corrected in this change. The GB300 arm already supplies `trainer.env` and documents why (`nccl-all-reduce.yaml:459-460`). The GB200 arm lists `oci-roce-env.yaml` and `oci-gb200-roce-env.yaml` under `env` for the same reason the args list both: the NCCL variable comes from the shared profile and the UCX one from the delta, and neither fragment repeats a name the other sets.
- **The loopback arms use `jobTemplatePatch`, not `jobTemplate`.** A second `jobTemplate.trainer.env` would replace the architecture block's env wholesale, dropping `NCCL_SHM_DISABLE`, `NCCL_P2P_DISABLE` and the `gb200-env.yaml` set. RFC 6902 `op: add` to `/spec/workload/trainJob/trainer/env/-` appends instead. Both files' GB300 arms already take this shape for the same reason.
- **Every new arm also includes `deps/oci-mlnxnics-comm.yaml`.** On OCI GB200 that fragment renders empty, because ADR-087 defaults `mlnxPerNode` to 0 there and the whole document is guarded on a positive count. Including it is what makes `mlnxPerNode: 8` work as an opt back in for a site that does run the device plugin, and it keeps the arm shaped like its GB300 sibling.

`oci-roce-mpirun-args.yaml` is reused for GB200. Its content is OCI-wide, not GB300-specific: it pins OpenMPI's own point-to-point and out-of-band traffic to TCP on eth0, and disables UCC and HCOLL. The disable exists because UCC calls `mca_coll_ucc_comm_query` during `MPI_Init` and SIGSEGVs when UCX reaches the mlx5 devices with GID index 0, before `NCCL_IB_GID_INDEX` takes effect (`_lib/nccl/mpi-disable-ucc-hcoll-args.yaml:4-8`). That is a property of OCI's GID configuration and the OpenMPI image, both shared with GB200. The fragment's header comment, which currently says "OCI GB300 RoCE mpirun args", is widened to match its scope.

### Where the hostPath opt-in renders

One fragment, `_lib/overrides/hostpath-rdma.yaml`, included once at the end of the `overrides:` list of each of the five communication entries and both training entries. It is the second member of `_lib/overrides/`, after `gb200-topology-key.yaml`.

The whole document is wrapped in `{{- if eq .RDMADeviceAccess "hostPath" }}`, so at any other value it renders to nothing and the include contributes no override at all. Inside the guard it emits a single override whose `when` is empty. An empty `WhenSpec` matches everything (`matchesWhen` returns true with no clauses set, and `summarizeWhen` already prints `<always>` for it), which is correct here: the opt-in is a statement about the cluster's RDMA plumbing, not about a platform or an architecture, and a toggle that silently does nothing outside OCI would be a trap.

The override body is a dependency patch on `{{ .EntryName }}-runtime`, merged into the entry's own TrainingRuntime by apiVersion/kind/name through `mergeOrAppendDependency`. All seven entries name their worker replicated job `node` and its container `node`, so one fragment covers both the MPI and the torch shapes. It adds, on that container only:

- `securityContext.privileged: true`. `mergeMaps` recurses into `securityContext`, so the base `capabilities.add: [IPC_LOCK]` survives alongside it.
- a `volumeMounts` entry and a pod `volumes` entry named `rdma-devices`, for `/dev/infiniband` with `type: Directory`.

The MPI launcher container is deliberately untouched. It runs `mpirun` as a coordinator with no GPU request and no RDMA traffic; the ranks run on the worker pods.

`type: Directory` rather than `DirectoryOrCreate` is deliberate: on a node with no RDMA devices the pod does not start at all, instead of silently mounting an empty directory that NCCL then reports as "no devices found" after the job has been scheduled. The failure mode is worth stating precisely, because it is not a clean one. Kubelet retries the mount, so the pod sits in `ContainerCreating` with a `FailedMount` event naming the missing path rather than terminating on its own.

`timeoutPerJob` is the only thing that bounds that wait, and before this change the entries did not all render one:

- The four MPI and nvswitch communication entries render `timeoutPerJob: {{ .TimeoutPerJob }}` (1h by default, `loader.go:67`). The Job times out and the Workflow reports it.
- `communication/nccl-loopback` rendered a bare `execution: {}`, so it got no bound and silently discarded a user's `spec.timeoutPerJob`. This change gives it the same `{{ .TimeoutPerJob }}` as its four siblings. It is a single-node, single-process loopback test with the same 1h default; nothing about it argues for being the one communication entry with no timeout.
- The two training entries rendered only `iterations`, so a missing `/dev/infiniband` hung them until an operator intervened, and an explicit `spec.timeoutPerJob` was silently discarded (issue #403 reproduces it with `7m`). This change gives both entries `execution: {timeoutPerJob: {{ .TimeoutPerJob }}}` like every other entry, with a 24h default in each entry's `meta.yaml`. The value is a backstop against never finishing, not a performance bound, and it mirrors `DefaultWorkloadRunTimeoutPerJob` (`pkg/catalog/loader.go:52-63`), which exists for the same reason. A tuned default would need measured runtimes the catalog does not have: `nemotron5-56b/configs/train.sh:51` sets `--distributed-timeout-minutes 230`, so the catalog-wide 1h would kill a healthy 56b run, and the `dcgm-level4` precedent at `diagnostics/dcgm-level4/meta.yaml:10` set 2h only after a recorded 1h31m field run. 24h cuts no legitimate run short and still ends a hung one within a day.

  On a training category the practical advice is to set `spec.timeoutPerJob` when enabling `rdmaDeviceAccess: hostPath`, since the default means learning about a node without `/dev/infiniband` in a day rather than in minutes. The operator-visible signal either way is a pod stuck in `ContainerCreating` with a `FailedMount` event naming `/dev/infiniband`.

`startupStallTimeoutSeconds` does **not** cover this on any entry, including the two that set it. `checkStallTimeout` needs a GoodputMeasurement (`job_controller.go:742-750`) and `startupStallAnchor` needs `gm.Status.ApplicationStartTime` or `gm.Status.StartTime` (`:1004-1020`); `StartTime` is only stamped after `podutil.IsPodRunning(worker-0)` passes (`goodputmeasurement_controller.go:488-491`, `:558-560`), and `IsPodRunning` is `phase == Running` (`pkg/podutil/discoverer.go:156-158`). A pod held in `ContainerCreating` never reaches that, so the anchor never exists and the detector never arms. Scheduling-stall detection is out too: `checkSchedulingBlocked` skips any pod that already has a `nodeName` (`job_controller.go:880`), and a pod failing a mount has been scheduled. The fragment's header comment records all of this so the next reader does not re-derive it.

## Implementation

- `api/v1alpha1/certification_types.go`: `RDMADeviceAccess string` on `CategoryOptions`, `+optional`, `+kubebuilder:validation:Enum=hostPath;devicePlugin`. The doc comment states what each value renders and that unset equals `devicePlugin`, because `controller-gen` copies it into the CRD description and that is what `kubectl explain` prints. `make manifests generate` regenerates the CRD and the deepcopy. The same file exports `RDMADeviceAccessHostPath` / `RDMADeviceAccessDevicePlugin` and `ValidRDMADeviceAccessValues`, so the CLI check below cannot drift from the marker.
- `pkg/certification/certification.go`: `readCertification` rejects an out-of-enum `rdmaDeviceAccess` at both the spec level and per category, next to the existing threshold-key check. The kubebuilder marker only binds server-side and offline render never reaches an API server, so `rdmaDeviceAccess: HostPath` would otherwise exit 0 and emit no mount and no privileged flag: a clean-looking manifest that still fails with `EPERM` on the cluster, handed to the operator who turned the option on specifically to avoid that. Other `CategoryOptions` enums accept a wrong value offline too, but none of them has a silent failure mode this close to the thing the field exists to fix.
- `pkg/catalog/entries/communication/nccl-loopback.yaml`: `execution: {}` becomes `execution: {timeoutPerJob: {{ .TimeoutPerJob }}}`, matching its four siblings. `pkg/catalog/entries/training/nemotron5-8b.yaml` and `nemotron5-56b.yaml` gain the same block, and their `meta.yaml` files gain `timeoutPerJob: "24h"`. See the hostPath section above.
- `pkg/catalog/catalog.go`: `RDMADeviceAccess string` on `BuildConfig`, documented next to `MlnxPerNode` and `NicResourceName`.
- `pkg/catalog/loader.go`: the matching `TemplateData` field with the `// Templates use: {{- if eq .RDMADeviceAccess "hostPath" }}` comment the struct's convention requires, and the assignment in `buildTemplateData`.
- `pkg/controller/certification_controller.go`: the field in the `catalog.BuildConfig` literal, and an arm in `ResolveOptions` so a per-category value beats the global one.
- `pkg/certification/certification.go`: the same field in the second `BuildConfig` literal. Both literals must be updated or offline `nvcrectl certification render` previews a different workflow than the controller applies, which is the defect that file's own comment at `:574-577` records.
- `pkg/catalog/entries/_lib/nccl/oci-gb200-roce-env.yaml`: new, one variable, with a header comment recording that it is a delta over `oci-roce-env.yaml` rather than a self-contained profile, why `NCCL_IB_GID_INDEX` is deliberately not repeated (the map-list constraint above), and that `NCCL_MNNVL_ENABLE` is not here because `gb200-env.yaml` (communication) and `gb200-training-base-env.yaml` (training) already carry it.
- `pkg/catalog/entries/_lib/nccl/oci-roce-mpirun-args.yaml`: header comment widened from GB300 to OCI.
- `pkg/catalog/entries/_lib/overrides/hostpath-rdma.yaml`: new, as described above.
- Seven entry files: one new OCI + GB200 arm each, and one `{{ lib "overrides/hostpath-rdma.yaml" . }}` include each.
- Docs: an `rdmaDeviceAccess` row in the spec-fields table of `docs/api-reference/certification.md`; a "Host RDMA device access" prose section in `docs/concepts/platform-detection.md`; a row for this ADR in `docs/designs/README.md`. The architecture-specific resources table in `platform-detection.md` is **not** touched: it describes what each platform and architecture request by default, and `rdmaDeviceAccess` is an opt-in that renders nothing unless set. ADRs are not in the Fern nav, so `docs/index.yml` is unchanged.
- `config/samples/`: no new sample. The field is opt-in and off, and the existing samples describe the default path.

`categoryOptionsSuffix` (`pkg/controller/certification_controller.go:1154`) **is** extended, with `hostrdma` and `dprdma` tokens. The precedent of leaving it alone, which `mlnxPerNode`, `nicResourceName` and `resources` follow, does not survive contact with what a collision costs here. Two categories of one domain and variant differing only in `rdmaDeviceAccess` is the natural way to compare the two access models, and without a token they resolve to one Workflow name: the second category's `Create` returns `AlreadyExists`, the owner check passes because the first Workflow belongs to the same Certification, and `checkActiveWorkflow` copies the first category's terminal condition onto the second. The report then shows a verdict for a configuration that never ran, with no event and no `Failed` condition. The two categories render genuinely different pods, so this is not a cosmetic collision. No existing Workflow name changes, because the token only appears when the field is set.

The same change makes offline `nvcrectl certification render` use the controller's naming rule instead of rebuilding the name itself. Render previously omitted the options suffix entirely, so any Certification with per-category options previewed under a name the controller never creates, and two categories differing only in options emitted two documents with one `metadata.name`, of which `render | kubectl apply -f -` kept only the last. `pkg/controller.WorkflowName` is now the single rule and `pkg/certification` calls it, which is the same argument that file's comment at `:574-577` makes about the two `BuildConfig` literals. The render goldens for the ten cases that set per-category options change name accordingly; nothing else in them moves. Each of the ten sets `maxSteps`, so each was already carrying an `-s<N>` suffix the controller applied and render did not.

### Testing plan

Goldens through `testutil.TestCaseParser`, per the package policy in CLAUDE.md.

A new suite, `pkg/certification/testdata/certification-render-rdma/`, modeled on `certification-render-mlnx/` and driven the same way (an `input.yaml` naming platform and GPU architecture, an `input_certification.yaml`, and an `expected.json`). The projection captures what both halves change and nothing else: per replicated job, the worker container's `securityContext`, `volumeMounts` and the pod `volumes`, plus the trainer's `args` and `env`. Cases:

- `oci-gb200-nccl`: the all-reduce arm renders the OCI RoCE args and the launcher's GID env. This is the before/after for defect 1 on the communication path.
- `oci-gb200-loopback`: the appended GID vars sit after, not instead of, the architecture block's env.
- `oci-gb200-training`: the new training arm renders `oci-roce-env.yaml` plus the GID pair.
- `oci-gb300-nccl-control` and `oci-l40s-nccl-control`: unchanged. These are the regression pins for the two OCI architectures that already worked, and they are what catches an arm inserted at the wrong point in the document.
- `oci-gb200-nccl-hostpath`: `rdmaDeviceAccess: hostPath`. Privileged, the mount, the volume, and `IPC_LOCK` still present.
- `oci-gb200-nccl-device-plugin`: the explicit value renders identically to unset.
- `aws-gb200-nccl-hostpath`: the opt-in is platform-independent, and the AWS EFA arm is otherwise untouched.

Two cases in the existing `certification-render-errors/` suite pin the CLI validation, one for the spec-level field and one for a category's `options`. Both use a realistic typo (`HostPath`, `hostpath`) rather than a nonsense string, since wrong case is the failure this check exists for.

Four cases in `render-orchestration-options/` pin the timeouts that nothing covered before: `loopback-honors-timeout` (a user's `45m` reaches the entry), `loopback-defaults-to-one-hour` (the catalog default applies when nothing is set), `training-honors-timeout` (a user's `7m`, the #403 reproduction, reaches `nemotron5-8b`) and `training-defaults-to-24h` (the `meta.yaml` default applies, not the catalog-wide 1h). Reverting either entry to its old shape turns its two cases red.

The mutation criterion from ADR-087 applies to the new guard as well: deleting the `{{- if eq .RDMADeviceAccess "hostPath" }}` wrapper must turn at least one golden red. Because the fragment's `when` clause is empty, a deleted guard renders the privileged patch in every case, so all five cases that leave the field unset catch it. What `oci-gb200-nccl-device-plugin` uniquely catches is a guard *narrowed* rather than deleted, for example to `ne .RDMADeviceAccess "devicePlugin"`: every unset case takes the same branch as before and stays green, and only the explicit-default case goes red.

Two more cases cover gaps the first pass left. `oci-gb200-hostpath-with-mlnx` sets `mlnxPerNode` and `rdmaDeviceAccess` together, the combination the Notes assert is valid and nothing tested; the golden shows the NIC resource request and the privileged mount on the same container, reaching it through different mechanisms. `hostpath-vs-deviceplugin-same-variant` lists one domain and variant twice, differing only in the field, and pins two distinct Workflow names; dropping the `categoryOptionsSuffix` arm collapses them to one and turns it red. The projection also now carries container `resources`, which it discarded before, so the AWS case pins that the dependency merge recurses into a container carrying EFA and GPU requests rather than replacing it.

Three cases in `cmd/integration/testdata/validation/` exercise the `Enum` marker against a real API server, which nothing did before: a wrong-case value at the spec level, a wrong-case value in a category's `options`, and both valid values accepted at once.

`cmd/integration/testdata/reconcile/certification-oci-gb200-nccl/expected.json` moves, because the rendered trainer args for that case are exactly what defect 1 was dropping. That golden is regenerated only after the diff is read and confirmed to be the intended args, and only with explicit permission.

Two existing mechanisms exercise the new template branches for free and neither substitutes for the goldens: `pkg/catalog/loader.go:403-407` renders every entry against a zero-value `TemplateData{}` at registration, and `TestEveryLibFragmentParsesThroughPlatform` (`pkg/platform/overrides_test.go:37`) asserts every `_lib/` fragment still parses through the platform renderer. Both prove a guard does not break the render. Neither says what it renders, and with zero-value data the false branch is the one taken, so a guard deleted outright leaves both green.

Render verification per the nvcrectl procedure in CLAUDE.md: OCI GB200 must emit `NCCL_IB_GID_INDEX`, `NCCL_IB_TC`, `NCCL_IB_SL` and `NCCL_IB_QPS_PER_CONNECTION`; OCI GB300, OCI L40S, AWS GB200 and Azure H100 counts must be unchanged; `rdmaDeviceAccess: hostPath` must add exactly one hostPath volume and one `privileged: true` per worker container, and unset must add none.

## Rationale

- **The fix is composition, not new tuning.** Every variable OCI GB200 starts receiving already exists in a fragment that OCI or GB200 already uses. The defect is that two overrides write the same field and the later one wins; the fix is an arm that writes that field once with both halves in it. Nothing here claims a new fact about GB200 hardware, which is why the GB300 arm's three hardware-specific variables stay behind.
- **Two root causes need two shapes.** Treating the training entries as an ordering problem would produce an arm that overrides nothing, and treating the communication entries as a missing arm would miss that placement is what makes them work. They are described separately for that reason.
- **The access model is a property of the cluster, so it belongs on the Certification, not in the catalog.** Whether RDMA arrives through a device plugin or through hostPath is a site decision made before NVCRE is installed. Encoding it as an OCI GB200 catalog default would be wrong for every OCI GB200 site that does run the plugin, and encoding it as detection would mean inferring a security posture from node labels. An explicit opt-in puts the decision where the person who knows the answer already is.
- **An enum, not a boolean.** `privileged: true` is the mechanism, not the intent. Naming the two access models leaves room for a third (a named device-plugin resource, say) without an API migration, and it makes `devicePlugin` a thing an operator can write down rather than an absence they have to infer. It is also what the user asked for: a toggle.
- **`/dev/infiniband` only is the defensible minimum.** The reporting cluster's working pod mounts six host paths, but five of them are either already present in the container or unrelated to the `open()` that was failing. The experiment isolates the device nodes as the missing piece. A broader mount set would be copying a configuration rather than fixing a defect, and each extra path is host surface the workload did not need.
- **Off by default resolves the DCGM collision without relitigating it.** The OCI DCGM arm records that CRI-O with device-plugin GPU injection rejects privileged containers. That is a real constraint for the clusters it describes, and the field changes nothing on them because nobody sets it. On the reporting cluster, privileged demonstrably works: the user ran `ib_write_bw` at 387 Gb/s in one. An operator who sets `hostPath` is asserting that their container runtime accepts privileged workloads, and they get a pod that fails to start if it does not. This ADR does not claim the DCGM comment is wrong, and does not change it.
- **ADR-016's preference is about portability, and this honors it.** "emptyDir for dshm (not hostPath): more portable" argues against hostPath as a *default*, and this change keeps every default exactly where ADR-016 left it. It adds a path for clusters where the portable option is not available, which is the case ADR-016 did not have in front of it.

## Consequences

- **OCI GB200 renders change for all seven entries.** This is the point of the change, and it is a behavior change for any site already running OCI GB200 certifications: the NCCL transport environment goes from effectively unset to the OCI RoCE profile. The expected effect is that cross-node collectives start working rather than failing at connection setup. It belongs in the release notes.
- **OCI GB200 MPI collectives also gain the TCP transport pinning and the UCC/HCOLL disable.** That is a broader change than the environment variables alone, and it is the piece of decision 1 with the least direct evidence on GB200 specifically: the SIGSEGV it prevents is documented on OCI, not on OCI GB200. The alternative, shipping GB200 with only `mpi-leading-args.yaml`, leaves a known OCI crash path open. If a site reports a regression from the MCA pinning, the arm can drop back to `mpi-leading-args.yaml` without touching anything else.
- **`privileged: true` becomes reachable from the Certification API, and it was not before.** `CertificationSpec` exposes no patch escape hatch: `jobTemplatePatch` lives on `OverrideSpec` in the Workflow API (`workflow_types.go:811`), which is written by catalog entries, not by the person submitting a Certification. An operator restricted to the Certification surface previously had no way to set a security context at all. This adds one, as a named, validated, defaulted-off enum where a typo is rejected by the API server rather than silently ignored, but it is a new capability on that surface and should be read as one.
- **The GID variables move from `trainer.env` alone to the shared profile plus a delta.** The communication arms previously set only `oci-gb200-roce-env.yaml` under `env`, which gave the MPI launcher the UCX variable and the NCCL one but none of the rest of the OCI profile. They now set `oci-roce-env.yaml` first, so the launcher's container environment matches what the ranks receive through `mpirun -x`. That is why `certification-oci-gb200-nccl/expected.json` goes from no `trainer.env` at all to eleven entries, and gains the OCI MCA block plus the RoCE `-x` pairs under `trainer.args`. Nothing is removed: the diff is +89/-0. `-x NCCL_IB_GID_INDEX=3` is not "preserved" but newly added, which is the whole point of the fix: the baseline golden at `decee44a` contains no occurrence of `NCCL_IB_GID_INDEX` anywhere, because the OCI RoCE set never reached GB200.
- **A cluster with Pod Security Standards enforced at `restricted` or `baseline` will reject the pod.** Nothing in NVCRE enforces or checks PSS, so the failure surfaces as a pod admission error, not as an NVCRE condition. Documented, not detected.
- **The empty `when` is now load-bearing.** `matchesWhen` returning true for an all-nil `WhenSpec` is what makes the opt-in platform-independent. It was already the code's behavior and `summarizeWhen` already had a `<always>` branch for it, but this is the first catalog override to rely on it.
- **`oci-gb300-roce-env.yaml` still repeats `NCCL_IB_GID_INDEX`, and that is latent.** It is safe today only because every arm that feeds it into `trainer.env` does so without also including `oci-roce-env.yaml` there. Making the GB300 fragment a delta the same way would touch the GB300 arms of six files, so it is left as it is and recorded here rather than changed in a PR about GB200. The new integration case pins the GB200 half against a real API server; the GB300 half has no equivalent pin.
- **`communication/nccl-loopback` gains a 1h default `timeoutPerJob` it did not have, and the two training entries gain a 24h one.** The loopback test finishes in minutes, so its bound should never be reached in practice. The training bound is deliberately generous for the opposite reason: a healthy run can take hours and the length depends on `maxSteps` and hardware. Both are behavior changes on every platform rather than only on OCI. A site relying on an unbounded Job now sees it time out, at 1h or 24h; a site that had set `spec.timeoutPerJob` and wondered why it had no effect on these three entries now gets what it asked for. The CLI already derived its `--wait` budget as if the 1h default applied to training (`deriveWaitTimeout`, `pkg/certification/certification.go:966`), so that derivation now reflects a bound the controller actually enforces.
- **`hostpath-rdma.yaml` would fail to execute through `pkg/platform`, which renders the same `_lib/` directory with a different data struct.** `platform.OverrideConfig` has no `RDMADeviceAccess` field, so `{{- if eq .RDMADeviceAccess "hostPath" }}` would error with `can't evaluate field`. This is latent rather than broken: `pkg/platform/overrides/workloadrun.yaml` includes no OCI blocks and does not reference this fragment, and five existing fragments share the same trap (`gcp-h100-nccl-image-patch-comm.yaml`, `gcp-h100-nccl-image-patch-loopback.yaml`, `gcp-h100-tcpxo-runtime-patch.yaml`, `gcp-h100-training-image-patch.yaml`, `nccl-perf-args.yaml`). `TestEveryLibFragmentParsesThroughPlatform` only parses, so it does not catch the class. Anyone wiring `_lib/overrides/` into the WorkloadRun path has to reconcile the two structs first.

## Alternatives Considered

- **Reorder the existing blocks so `platform: oci` comes after the architecture block.** Rejected: it fixes GB200 by breaking GB300. The GB300 arm's `trainer.args` would then be overwritten by the OCI arm's, losing the adaptive routing and DMABUF settings. It also fixes nothing for the two training entries, whose problem is a missing arm, and it would leave the file's ordering comments describing an order it no longer has.
- **Give override matching a specificity ranking, so a two-clause `when` beats a one-clause `when`.** Rejected for this change, though it is the real fix for the class of bug. Every ordering comment in every entry (`nccl-all-reduce.yaml:352`, `:425-426`, `:456-457`, and the matching lines in six other files) encodes the current semantics, and the `AppliedOverride` indices recorded in Workflow status are positional. Changing the resolution order is an ADR-012 amendment with a blast radius across every golden in the repository, not a fix for one platform's missing arm.
- **A single `_lib/overrides/oci-gb200-roce.yaml` emitting the whole arm, included by all seven entries.** Rejected: the arm's body differs by entry (MPI args, torch env, and a JSON Patch), so the fragment would need to branch on the entry, which is harder to read than seven explicit blocks and breaks the house style of one visible block per platform-architecture pair.
- **A boolean `privileged` or `hostPathRDMA` field.** Rejected: it names the mechanism rather than the decision, leaves no room for a third access model, and gives an operator no way to write down that they are deliberately on the device-plugin path.
- **Mount the full set the user's working pod mounts (`/dev/infiniband`, `/sys`, `/proc`, `/sys/bus/pci`, `/sys/class/infiniband`, `/sys/class/net`).** Rejected: `/sys` is already mounted read-only in every container, so four of those are already reachable, and the user's own experiment isolates the device nodes as the only thing `open()` was failing on. Copying a working configuration wholesale would widen the host surface past what the evidence supports.
- **Grant capabilities instead of privileged (`SYS_ADMIN`, `NET_RAW`, `IPC_LOCK`).** Rejected: it does not work. The device cgroup allowlist is built from requested resources, and no capability modifies it. The user tested exactly this, with `IPC_LOCK`, and `open()` on `/dev/infiniband/uverbs0` returned `Operation not permitted` while the device node was visible.
- **Have the site install a generic RDMA device plugin (`k8s.v1.cni.cncf.io` RDMA shared-device plugin or similar) and keep NVCRE on the device-plugin path.** Rejected as a prerequisite, not as a bad idea. It is the better long-term posture: a device plugin advertises a resource, kubelet writes the device cgroup entries from that request, and nothing needs privilege. But it is a cluster-infrastructure change on a cluster NVCRE is being asked to certify as it stands, it has to be installed and validated before any certification can run, and NVCRE has no way to install it. The site already has a working RDMA story for its Slurm workloads through hostPath; asking them to re-plumb it to run a readiness test inverts which side is being tested. If the plugin does get installed, `rdmaDeviceAccess` goes back to unset and `mlnxPerNode` / `nicResourceName` take over, which is exactly why the field is an enum naming both models rather than a boolean.
- **Make it a WorkloadRun-only capability and leave Certification alone.** Rejected: it is the Certification path that the report is about. WorkloadRun accepts arbitrary `volumes` and `volumeMounts` (`api/v1alpha1/workloadrun_types.go:255-259`) but has no security context field at all, so it can mount the device tree and still not grant the device cgroup entries: the same `EPERM` the Context records. WorkloadRun therefore has no hostPath RDMA path today either, and giving it one is a separate change. Telling a site to hand-write every catalog NCCL test as a WorkloadRun is not a certification story in any case.
- **Add a generic `options.env` map so the four NCCL variables can be set per run.** Rejected for this change, and separately from the device-access decision. Decision 1 delivers the three variables that exist, and the fourth (`NCCL_IB_HCA`) is unset on purpose. A general env surface raises its own questions (precedence against catalog overrides, which container it lands on, whether it can unset) that the report does not force.

## Notes

- **The device cgroup, not file permissions, is what blocks the nonprivileged case.** This is worth recording because the symptom (a visible device node that will not open) reads like a permissions problem and invites a `chmod`, a supplemental group, or a capability, none of which help.
- **Setting `hostPath` silently drops seccomp confinement on the training entries.** Both set `seccompProfile: RuntimeDefault` at pod level (`nemotron5-8b.yaml:101-103`), and that profile stops applying to the privileged container: Kubernetes documents that "it is not possible to apply a seccomp profile to a container running with `privileged: true`... Privileged containers always run as `Unconfined`." The pod spec still reads `RuntimeDefault`, so the manifest does not show it. The fragment leaves the pod-level `securityContext` alone because removing the profile would also unconfine the sidecars, but an operator turning on `hostPath` should know that the worker container loses seccomp as well as gaining the device cgroup, and that is part of what the opt-in is asserting.
- **`mlnxPerNode` and `rdmaDeviceAccess` are independent and both can be set.** A site running both an SR-IOV device plugin and hostPath devices gets both, which is valid. The common cases are one or the other. `certification-render-rdma/oci-gb200-hostpath-with-mlnx` pins the combination, since nothing else sets both at once.
- **`NCCL_IB_HCA` stays unpinned.** The reporting user asked whether it could be configured. It is deliberately absent from every OCI fragment so NCCL auto-detects, matching what ADR-075 chose for on-prem. Pinning it would require knowing the device names, which vary by shape.
- **No UAT coverage for OCI.** `test/uat/testdata/` covers aws, gcp and togetherai only, so neither half of this change is exercised by the KWOK UAT suite. The render goldens and the integration case are the coverage.
